# Player Generation System — Technical Specification

**Document Type:** Engine Technical Specification  
**Status:** Implementation Ready  
**Scope:** Initial senior squad generation, youth academy generation, division-based player quality, player origin metadata, anti-reroll safeguards, deterministic generation, statistical balancing, and compatibility with the existing player development/decay system  
**Out of Scope:** Changes to player growth/decay formulas, transfer market rules, scouting systems, training facilities, coaching, morale, injuries, retirement logic

---

# 1. Purpose

This specification defines the player generation system for a persistent multiplayer football pyramid.

The system MUST:

- remove `club.level` entirely;
- use the club's current division as the only competitive-strength input for newly generated senior squads;
- use the club's current division plus its highest-ever division as the only club-strength inputs for youth academy generation;
- generate realistic-looking squads statistically rather than through hard-coded star/starter/bench roles;
- ensure higher divisions are stronger on average while preserving substantial player-quality overlap between divisions;
- allow lower-division clubs to generate rare excellent players;
- allow good players to emerge naturally and move upward through the transfer market;
- keep player birth quality independent from the existing player development-rate, decline-age, volatility, and activity systems;
- use a small, easy-to-tune set of generation parameters;
- preserve deterministic simulation through seeded RNG;
- prevent academy reroll exploits and duplicate generation;
- remain mathematically compatible with the existing player development/decay system.

The system MUST NOT attempt to predetermine a player's entire career.

Generation determines how good the player is when created.

The existing development system determines how that player changes afterward.

---

# 2. Core Design Principle

Every player's career MUST emerge from two mostly independent layers:

```text
STARTING QUALITY
some bad
many average
some good
rare great

        +

CAREER TRAJECTORY
slow/normal/fast development
different decline ages
different volatility
different activity histories
```

The intended result is that two equally rated young players may have very different careers.

Examples:

```text
Bad at 17 + high development rate + regular play
→ can become good

Great at 17 + low development rate + early decline
→ may plateau early

Average at 17 + high development rate + late decline
→ may become excellent

Great at 17 + high development rate + late decline
→ rare generational outcome
```

The generation system MUST NOT compensate for these future differences.

For Version 1:

```text
Corr(startingQuality, developmentRate) = 0
Corr(startingQuality, declineStartAge) = 0
Corr(startingQuality, developmentVolatility) = 0
```

The development profile remains generated exactly by the existing development system.

`club.level` MUST be removed from the game model.

The implementation agent MUST search all backend, frontend, migration, API, serialization, test, and UI code for:

```text
overallCap
TIER_BOUNDS_HIGH
```

Any logic that uses club level to determine:

```text

```

MUST be removed or rewritten.

Do NOT replace `club.level` with a hidden equivalent.

The only club-quality hierarchy is division.

# 4. Canonical Division Strength

Every division-sensitive generation calculation MUST use one canonical normalized function.

Define:

```text
D = division number
N = total number of divisions
```

with:

```text
Division 1 = strongest
larger division number = weaker
```

Use:

\[
S(D)=
1-
\frac{\ln(1+k(D-1))}
{\ln(1+k(N-1))}
\]

where:

```text
S(D) ∈ [0,1]
```

and:

```text
S(1) = 1
S(N) = 0
```

Special case:

```text
if N <= 1:
    S = 1
```

`k` controls curve shape.

It SHOULD be an internal engine constant rather than a frequently tuned gameplay setting.

The intended effect is:

```text
D1 → D2 difference > D2 → D3 difference > D3 → D4 ...
```

This keeps lower divisions closer together and prevents the bottom of the pyramid from becoming excessively weak.

# 5. Minimal Tuning Philosophy

The generation system SHOULD expose as few quality-balance parameters as possible.

The preferred quality tunables are:

```text
PLAYER_QUALITY_SPREAD
DIVISION_STRENGTH_SPREAD
ACADEMY_DIVISION_INFLUENCE
```

Structural gameplay settings MAY remain configurable:

```text
senior squad size
academy roster limit
seasonal academy intake count
academy age range
```

The system SHOULD NOT expose independent tuning variables for:

```text
star count
starter count
bench quality
club-strength variance
player-specific variance
role offsets
young-age mixture
prime-age mixture
veteran-age mixture
division-specific OVR tables
potential variance per division
academy quality by division
```

These outcomes MUST emerge from formulas and statistical distributions.

# 6. Global Player Quality Distribution

Player quality MUST use a bell-shaped distribution.

For generation:

\[
Z \sim TN(0,1,-3,3)
\]

where `TN` is a true truncated normal distribution.

Interpretation:

```text
Z ≈ 0      ordinary player
Z ≈ +1     good player
Z ≈ +2     excellent player
Z ≈ +2.5   rare elite outlier
Z ≈ +3     extreme outlier

negative values behave symmetrically
```

This naturally produces:

```text
many average players
fewer good players
few excellent players
few very bad players
rare extreme outliers
```

The implementation MUST use true truncated-normal sampling.

It MUST NOT sample an unbounded normal and then clamp the result, because clamping creates artificial concentrations at the boundaries.

---

# 7. Player Quality Spread

Define one global quality spread:

```text
PLAYER_QUALITY_SPREAD = σ
```

This controls how different players generated in the same environment can be.

Higher `σ`:

```text
more weak outliers
more elite outliers
more squad variation
```

Lower `σ`:

```text
players cluster more tightly around the mean
```

This one value replaces separate concepts such as:

```text
player variance
star variance
bench variance
club variance
```

---

# 8. Division Strength Spread

Define:

```text
DIVISION_STRENGTH_SPREAD
```

as the total expected strength difference from the lowest division to the highest division.

Let:

```text
μ_base = canonical overall baseline
```

Then:

\[
\mu(D)
=
\mu_{base}
+
DIVISION\_STRENGTH\_SPREAD \times S(D)
\]

The implementation agent SHOULD derive `μ_base` from the current game's valid player/OVR scale and existing balance rather than hard-code separate division means.

There MUST NOT be:

```text
D1 mean setting
D2 mean setting
D3 mean setting
...
```

All divisions use the same function.

---

# 9. Core Balance Ratio

The most important statistical balance metric is:

\[
R=
\frac{\Delta\mu}{\sigma}
\]

where:

```text
Δμ = mean difference between two divisions
σ  = PLAYER_QUALITY_SPREAD
```

Interpretation:

```text
R too large:
divisions behave like isolated talent pools

R too small:
divisions are almost indistinguishable

R moderate:
division averages differ,
but good lower-division players overlap strongly with higher divisions
```

Calibration SHOULD focus primarily on this dimensionless ratio.

---

# 10. Senior Player Generation

New senior squads MUST use only:

```text
current division
```

For each generated senior player:

\[
OVR^*_{senior}
=
\mu(D)
+
\sigma Z
\]

where:

```text
Z ~ TN(0,1,-3,3)
```

`OVR*` is a target overall used to drive skill generation.

The final displayed OVR MUST continue to be derived from generated skills through the existing OVR calculation.

No player is explicitly generated as:

```text
star
starter
rotation
bench
depth
```

Those roles emerge naturally from the distribution.

---

# 11. Why Explicit Squad Roles Are Not Needed

For a squad of `n` independently generated players:

\[
X_i \sim TN(\mu(D),\sigma)
\]

the resulting order statistics naturally create:

```text
a strongest player
a few very strong players
many average players
a few weak players
a weakest player
```

Different clubs in the same division will naturally have different roster shapes.

Examples:

```text
Club A:
one outstanding player
several solid players
average depth

Club B:
no major star
many above-average players

Club C:
two excellent players
weaker lower half
```

No extra club-strength variable is required.

---

# 12. Natural Club-Level Variation

If a club has `n` generated players from a distribution with standard deviation `σ`, its sample mean naturally varies with:

\[
SE(\bar X)=\frac{\sigma}{\sqrt{n}}
\]

Therefore some newly generated clubs will naturally be stronger or weaker than others even when they belong to the same division.

Do NOT add a separate `clubStrengthShock`.

Statistical sampling already provides club-level variance.

---

# 13. Cross-Division Overlap

All divisions MUST use the same `σ`.

Only the mean changes.

Therefore:

\[
D1 \sim TN(\mu_1,\sigma)
\]

\[
D2 \sim TN(\mu_2,\sigma)
\]

etc.

This guarantees overlap as long as `Δμ / σ` is kept moderate.

The system MUST permit outcomes such as:

```text
excellent D2 player > average D1 player
excellent D3 player > weak D1 player
rare D5 player = future D1-quality player
```

The system MUST NOT impose division-based player maximums or minimums.

---

# 14. Senior Squad Size

Initial squad size is a structural game rule.

Prefer one canonical configured squad size rather than:

```text
25 + random(0–5)
```

unless variable squad size has a separate gameplay purpose.

The quality model itself MUST NOT depend on squad size.

---

# 15. Senior Position Generation

Position generation MUST guarantee a playable roster.

Use one canonical roster-position structure appropriate to the game's supported positions.

The implementation MAY randomize exact positional subtypes within valid constraints.

Position generation MUST NOT introduce quality bonuses.

Quality and position are separate.

---

# 16. Senior Age Generation

Senior age generation SHOULD use one mathematically derived truncated normal rather than a manually tuned mixture of young/prime/veteran groups.

The existing development system defines:

```text
growth reference age = 18
mean decline-start age = 30
```

Use these values to derive a sensible central senior age.

Recommended:

\[
\mu_{seniorAge}
=
\frac{18+30}{2}
=
24
\]

Derive spread from the same interval:

\[
\sigma_{seniorAge}
=
\frac{30-18}{4}
=
3
\]

Then sample:

\[
Age \sim TN(24,3,18,38)
\]

or equivalent integer/fractional age handling compatible with the current player model.

These values are derived from the development model rather than independently tuned.

---

# 17. Senior Development Profiles

After current senior ability and age are generated, generate the normal development profile exactly as defined by the existing development system:

```text
declineStartAge
developmentRate
developmentVolatility
```

Do NOT condition those values on:

```text
division
player quality
club
human/AI
```

This intentionally allows:

```text
great player + low development rate
great player + early decline
average player + high development rate
average player + late decline
```

# 18. Youth Academy Inputs

Youth generation uses exactly two club-strength inputs:

```text
currentDivision
highestDivisionReached
```

No other club-strength variable is allowed.

---

# 19. Highest-Ever Division

Add:

```ts
club.highestDivisionReached
```

Because lower numbers represent stronger divisions:

```ts
highestDivisionReached =
    Math.min(
        highestDivisionReached,
        currentDivision
    );
```

New clubs:

```text
highestDivisionReached = initialDivision
```

Existing clubs:

```text
if reliable historical division data exists:
    derive the best historical division
else:
    highestDivisionReached = currentDivision
```

The value MUST never worsen after relegation.

---

# 20. When Highest-Ever Division Updates

Do NOT update the field when promotion becomes mathematically guaranteed.

Update only when the club actually begins a season in that division.

Lifecycle:

```text
season ends
↓
promotion/relegation resolved
↓
next-season divisions assigned
↓
new season begins
↓
highestDivisionReached updated
↓
academy intake generated
```

Thus a promoted club receives the new current-division academy influence only when it is actually participating in the promoted division.

---

# 21. Academy Pedigree

Calculate:

```text
currentStrength =
    S(currentDivision)

historicStrength =
    S(highestDivisionReached)
```

Then:

\[
P_A =
0.65S(current)
+
0.35S(highestEver)
\]

where:

```text
0 <= P_A <= 1
```

The 65/35 split is the Version 1 default.

The current division remains more important than historical pedigree.

This means:

```text
current D4 / highest D1
```

has a better academy expectation than:

```text
current D4 / highest D4
```

but still does not behave like a current D1 club.

---

# 22. Academy Division Influence

Define one small generation parameter:

```text
ACADEMY_DIVISION_INFLUENCE
```

Express it in units of player-quality standard deviation.

For youth:

\[
Z_{academy}
=
Z
+
ACADEMY\_DIVISION\_INFLUENCE \times P_A
\]

where:

\[
Z \sim TN(0,1,-3,3)
\]

The Version 1 calibration SHOULD keep this effect small compared with natural talent variation.

Conceptually:

```text
maximum academy shift ≈ a small fraction of 1σ
```

The exact selected value MUST be established by simulation.

Individual talent MUST remain more important than academy pedigree.

---

# 23. Youth Starting Quality

Youth quality MUST be generated directly.

Do NOT generate a predetermined final career target.

For each youth:

\[
OVR^*_{youth}
=
\mu_{youth}(age)
+
\sigma Z_{academy}
\]

where:

```text
μ_youth(age) = expected current ability at that age
σ            = PLAYER_QUALITY_SPREAD
```

A youth can therefore be:

```text
bad at birth
average at birth
good at birth
exceptional at birth
```

independently of how quickly he later develops.

---

# 24. Youth Age Mean Must Come From Development Mathematics

Do NOT configure separate arbitrary means such as:

```text
16yo mean = X
17yo mean = Y
18yo mean = Z
19yo mean = W
```

Instead derive age differences from the existing growth curve.

Let:

```text
μ18 = canonical youth reference mean at age 18
```

Then:

\[
\mu_{youth}(age)
=
\mu_{18}
+
\int_{18}^{age}
E[Growth(x)]dx
\]

using the existing development model's expected growth behavior.

For expected-value calculation use:

```text
developmentRate = 1.0
random factor = 1.0
reference activity = configured neutral/default activity or a single documented generation reference
```

The coding agent MAY calculate this through numerical integration or the production tick functions.

Do NOT manually tune four separate youth-age penalties.

---

# 25. Development Model Compatibility

The generation system MUST use the existing development specification as authoritative.

The following existing development mechanisms MUST remain unchanged:

```text
precise age calculation
age growth curve
decline curve
developmentRate distribution
developmentVolatility distribution
declineStartAge distribution
activity modifiers
daily tick scaling
random-factor rules
fractional skill accumulation
training-weight distribution
weekly potentialGrowth()
```

Generation MUST adapt to these mechanics rather than modify them.

---

# 26. Youth Development Profile Independence

After current youth quality is generated, assign the existing development profile independently.

For Version 1:

\[
Corr(startingQuality,developmentRate)=0
\]

\[
Corr(startingQuality,declineStartAge)=0
\]

\[
Corr(startingQuality,developmentVolatility)=0
\]

This is required.

Do NOT make higher-quality youth systematically:

```text
develop faster
decline later
be more stable
```

The current quality draw and career-development draw are separate.

---

# 27. Potential

The current engine already has a `player.potential` growth ceiling.

This system MUST preserve it.

Potential generation SHOULD remain simple and SHOULD NOT introduce multiple division-specific tuning variables.

Use:

```text
current ability
+
expected remaining growth
+
one random headroom component
```

Conceptually:

\[
Potential
=
OVR
+
E[RemainingGrowth(age)]
+
H
\]

where:

```text
H = bounded random headroom term
```

The implementation agent MUST inspect the current `potentialGrowth()` semantics before finalizing the exact formula.

Required invariants:

```text
potential >= overall
potential <= global maximum
```

Potential MUST NOT depend strongly on division.

Academy pedigree MUST NOT create a separate large potential bonus.

The existing development system, activity, developmentRate, decline timing, and potential-growth logic should remain the main determinants of how much of that ceiling is reached.

---

# 28. Potential Must Not Be a Career Prophecy

The implementation MUST preserve:

```text
starting quality != guaranteed final quality
```

A player's career outcome must remain affected by:

```text
developmentRate
activity
declineStartAge
volatility
potential growth
```

Potential is a ceiling/safety mechanism, not a deterministic predicted OVR.

---

# 29. Tier

Player tier MUST no longer be generated from club level or division.

Generate the player first.

Then classify tier from age-normalized player quality.

Preferred method:

1. determine the player's standardized quality score;
2. map it to percentile bands of the standard normal distribution.

Example five-band structure:

```text
bottom ~10%
next ~20%
middle ~40%
next ~20%
top ~10%
```

Equivalent standard-normal thresholds are approximately:

```text
-1.28
-0.52
+0.52
+1.28
```

Map these bands to the game's existing tier ordering.

Because tier currently affects `potentialGrowth()`, the coding agent MUST audit all tier consumers before changing semantics.

---

The generator MAY internally use:

```text
Z
academy-adjusted Z
percentile
```

during generation.

These do not need to persist on the player.

Do NOT expose them to clients.

Persist only actual game state:

```text
skills
overall
potential
tier

DOB/age
contracts

```

# 31. Initial Academy Generation

Initial club creation needs an academy immediately.

Use:

```text
generateInitialAcademy()
```

This MUST use the same statistical youth-quality model as normal seasonal academy intake.

There is no special "new club youth quality" formula.

Only the number/age distribution of generated youth may differ.

---

# 32. Seasonal Academy Intake

Remove the existing:

```text
top academy back up to target
```

behavior.

This permits an exploit:

```text
release bad youths
↓
academy below target
↓
receive replacement lottery tickets
```

Replace it with:

```text
ACADEMY_ROSTER_LIMIT
SEASONAL_ACADEMY_INTAKE
```

At seasonal intake:

```text
availableSlots =
    rosterLimit - currentAcademyCount

intakeCount =
    min(
        seasonalIntake,
        availableSlots
    )
```

A manager may release players to create space.

Releasing players MUST NOT increase the seasonal intake quota.

---

# 33. No Mid-Season Replacement Generation

Once seasonal academy intake has occurred:

```text
release youth
```

MUST NOT generate a replacement.

The next opportunity is the following scheduled seasonal intake.

---

# 34. Academy Intake Idempotency

Academy generation MUST be idempotent.

Track an intake identity such as:

```text
clubId + seasonId
```

or an equivalent persisted intake record.

If the same rollover/intake is executed again because of:

```text
retry
server restart
duplicate scheduled job
transaction replay
```

no new youth may be generated.

---

# 35. Club Creation Idempotency

Initial senior squad and academy generation MUST also be idempotent.

Retrying club creation MUST NOT reroll:

```text
players
skills
ages
potential
development profiles
```

Generation SHOULD either:

- use deterministic server-private seeds tied to the creation event; or
- atomically persist generation results and reuse them on retry.

---

# 36. RNG Requirements

All generation MUST use the engine's deterministic seeded RNG abstraction.

Do NOT call:

```ts
Math.random()
```

inside generation logic.

The central RNG SHOULD support:

```ts
uniform()
normal()
truncatedNormal()
beta()
```

The development system already requires these statistical primitives.

Generation MUST reuse the same infrastructure.

---

# 37. Server-Private Seeds

If deterministic seeding is used, future player-generation results MUST NOT be predictable from public client data.

Seed derivation SHOULD include private server entropy plus stable identifiers such as:

```text
world/server secret
club ID
season ID
generation type
player slot
```

Do NOT reuse a publicly recoverable match-simulation seed.

---

# 38. Generated Skills

The generator MUST NOT directly set OVR as an authoritative stored value.

For each player:

```text
target OVR
↓
position
↓
existing position/tactical skill generator
↓
skills
↓
existing OVR calculation
```

If the generated skills produce an OVR too far from the statistical target, the generator MAY rescale/retry deterministically.

Use a bounded retry count.

No unbounded generation loops are allowed.

---

# 39. Skill and OVR Bounds

Use the game's global valid skill and OVR bounds.

Do NOT use discontinuous corrections such as:

```text
if value < 5:
    value = 10
```

Use mathematically explicit truncated/bounded generation.

The theoretical range must be shared by all divisions.

No division-specific ability ceiling is allowed.

---

# 40. Remove Club/Division Development Caps

If the current system has:

```text
overallCap(club)
```

derived from `club.level`, remove it.

Do NOT replace it with:

```text
overallCap(division)
```

A lower-division player must be able to develop into a top-division-quality player while still owned by the lower-division club.

The player's own potential remains the relevant growth ceiling.

---

# 41. Human and AI Clubs Use Identical Generation

Human and AI clubs MUST use the same generation services.

Do NOT retain:

```text
human level = 15
AI level based on division
```

or any equivalent.

Both should call the same canonical operation:

```ts
generateInitialClubSquad({
    division,
    rng,
})
```

Human/AI ownership is irrelevant to player quality.

---

# 42. Reuse Generation Everywhere

The same production generator SHOULD be reused for all systems that need newly created club players, including:

```text
human club creation
AI filler club creation
league expansion
replacement club creation
financial-intervention replacement players
administrative regeneration
```

If the rule says:

```text
generate players equivalent to a new club in this division
```

the implementation should literally use the same generator.

---

Existing:


# 48. Statistical Generation Tests

Generate at least:

```text

```

per major statistical test.

Validate:

```text

sample mean is approximately expected
sample standard deviation is approximately expected
center values are much more common than extremes
+2σ outcomes are uncommon
+2.5σ outcomes are rare
+3σ outcomes are extremely rare
```

Use tolerances rather than exact counts.

# 70. Final Design Principle

The player-generation system determines:

```text
How good is this player when he enters the game?
```

The player-development system determines:

```text
What happens to him afterward?
```

Higher divisions have better players because their distributions have higher means.

Lower divisions remain relevant because all divisions share the same statistical spread and theoretical player-quality range.

Academy pedigree slightly shifts youth quality, but random individual talent remains more important.

The intended long-term ecosystem is:

```text
lower division
↓
rare good prospect
↓
development
↓
player becomes valuable
↓
higher club buys him
↓
talent migrates upward
```

This mobility is an emergent consequence of player generation, development, and the transfer market rather than a hard-coded division restriction.
