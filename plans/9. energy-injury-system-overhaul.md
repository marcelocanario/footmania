# Footmania Energy & Injury System Overhaul

**Status:** Implementation-ready specification  
**Scope:** Player Energy, in-match fatigue, recent workload, recovery, match injuries, training injuries, injury severity, return-to-fitness, rare lasting setbacks, AI rotation, UI/API behavior, migration, and validation.

---

## 1. Goals and non-negotiable rules

This overhaul replaces the current stamina-capacity/rest-quality/minutes-last-72h logic with one player-facing metric and two internal mechanisms.

### Player-facing rule

Players see only:

```text
Energy: 0–100
```

Do **not** add a separate visible `stamina`, `fitness`, `condition`, `workload`, or `fatigue` numeric attribute.

### Internal rule

The engine may internally track:

```text
liveEnergy       // current Energy during a match
recentLoad       // persistent exponentially-decaying recent workload
```

`liveEnergy` is the same Energy concept the player sees. It is fractional while a match is running and committed to `Player.energy` after the match.

`recentLoad` is hidden model state. It explains why two players at the same Energy can have different recovery and injury risk.

Example:

```text
Player A:
Energy = 70
recentLoad = low
reason = he started at 100 and has played 85 minutes today

Player B:
Energy = 70
recentLoad = high
reason = he entered today already tired after several consecutive matches
```

The UI must still show only Energy, optionally with qualitative workload text.

### Required gameplay behavior

The formulas must produce the following tendencies without hard-coded rotation rules:

```text
young/prime normal outfield player:
    can usually play 3–4 consecutive full matches
    before rotation becomes clearly advantageous

older player:
    rotation pressure should become meaningful after roughly 2–3 full matches

resting for one scheduled league match:
    should normally restore a young/prime player to approximately full Energy
    if he was rotated after 3–4 consecutive starts

goalkeepers:
    lose much less Energy than outfield players

high pressing:
    materially increases Energy expenditure

good physical attributes:
    modestly reduce Energy expenditure and improve recovery

low Energy:
    reduces match effectiveness continuously
    increases match injury risk

recentLoad:
    slows recovery
    increases injury risk
    decays automatically with rest
```

There must be no rule such as:

```text
if consecutiveMatches >= 4:
    force rest
```

All rotation pressure must emerge from the equations.

# 2. Compatibility with the current approved calendar and simulator

The current approved league calendar derives:

```text
roundsPerSeason = league.turns × (league.teams - 1)
matchSpacingDays = restDaysBetweenMatches + 1
seasonDays = lastLeagueMatchDayIndex + 1 + interseasonDays
```

With the current production defaults:

```text
roundsPerSeason = 14
matchSpacingDays = 2
seasonDays = 35
interseasonDays = 7
league match days = Season Days 2, 4, 6, ... 28
```

The Energy/injury model must consume these derived values from `SeasonCalendarService`.

It must never independently hard-code:

```text
14 matches
2-day spacing
35-day season
7 interseason days
```

Those are current derived outputs, not model assumptions.

The current match simulator already applies Energy through a readiness multiplier to usable player attributes. Keep that architectural rule: Energy modifies the actual skills used in the simulator exactly once.

Remove the existing derived `staminaCapacity`, `restQuality`, `minutesPlayedLast24h`, and `minutesPlayedLast72h` fatigue logic from the final system.

# 5. Player persistence changes

Keep:

```text
Player.energy
```

as the only player-visible condition number.

Add:

```ts
recentLoad: number // Float, default 0
```

Remove or stop using persisted/recomputed fields whose sole purpose was the old workload model.

Replace mutable weekly-decrement injury semantics with absolute game-day semantics.

Use:

```ts
injuryUntilAbsoluteGameDay: number | null
injuryInitialGameDays: number | null
injuryEquivalentRealDays: number | null
injuryCause: "MATCH" | "TRAINING" | null
```

Do not keep `injuryDays` as an independently decremented authoritative value.

For API/UI compatibility, derive:

```text
injuryDaysRemaining =
    if injuryUntilAbsoluteGameDay == null:
        0
    else:
        max(
            0,
            injuryUntilAbsoluteGameDay
            - currentAbsoluteGameDay
            + 1
        )
```

Player unavailable rule:

```text
injured =
    injuryUntilAbsoluteGameDay != null
    AND
    currentAbsoluteGameDay <= injuryUntilAbsoluteGameDay
```

When:

```text
currentAbsoluteGameDay > injuryUntilAbsoluteGameDay
```

clear the injury metadata atomically after the return-to-fitness Energy rule has been applied.

This eliminates the current bug where an "injury day" decreases only during a weekly update.

```text
physicalSkill ∈ [0,100]
```

# 7. In-match Energy model

## 7.1 Pressing factor

Let manager pressing be `pressing ∈ [0,100]`.

Use:

```text
pressFactor =
    exp(
        pressLogRange
        * (pressing - 50) / 50
    )
```

With Version 1:

```text
pressing =   0 → factor ≈ 0.835
pressing =  50 → factor = 1.000
pressing = 100 → factor ≈ 1.197
```

This is preferable to a linear percentage because high and low pressing become symmetric in log-space.

---

## 7.2 Physical fatigue factor

```text
physicalFatigueFactor =
    exp(
        -physicalFatigueLogRange
        * (physicalSkill - 50) / 50
    )
```

With Version 1:

```text
physicalSkill =   0 → ≈ 1.197
physicalSkill =  50 → 1.000
physicalSkill = 100 → ≈ 0.835
```

Physical quality matters, but it does not dominate player condition.

---

## 7.3 Age fatigue factor

Do not use a logarithmic age penalty.

Use a convex post-prime curve:

```text
ageFatigueYears =
    max(0, age - 27)

ageFatigueFactor =
    exp(
        0.0035
        * ageFatigueYears^1.6
    )
```

Approximate values:

```text
age 27 → 1.000
age 30 → 1.021
age 32 → 1.047
age 35 → 1.102
age 38 → 1.176
age 40 → 1.236
```

Young and prime players are essentially unaffected. The curve accelerates only after the late twenties.

---

## 7.4 Low-Energy acceleration

As Energy falls, the same work becomes harder:

```text
lowEnergyFactor =
    1
    + 0.25
      * (1 - liveEnergy/100)^1.5
```

This is intentionally mild at ordinary Energy levels and becomes stronger only when a player is already tired.

---

## 7.5 Local involvement factor

Reuse the formation/zone involvement weight already calculated by the simulator:

```text
zoneInvolvementWeight ∈ [0,1]
```

Then:

```text
involvementFactor =
    0.80
    + 0.40 * zoneInvolvementWeight
```

Therefore:

```text
minimum = 0.80
neutral = 1.00 when involvement = 0.50
maximum = 1.20
```

Do not introduce another activity map.

---

## 7.6 Energy expenditure

For elapsed actual match-clock time:

```text
dtMinutes = elapsedMatchClockSeconds / 60
```

Reference loss is defined so a neutral 90-minute midfielder at age <=27, physicalSkill 50, pressing 50, involvement 0.50 loses about 18 Energy.

```text
energyLossRatePerMinute =
    (18 / 90)
    * roleLoad
    * pressFactor
    * physicalFatigueFactor
    * ageFatigueFactor
    * lowEnergyFactor
    * involvementFactor
    * config.energy.matchLossScale
```

Then:

```text
liveEnergyNext =
    max(
        0,
        liveEnergy
        - energyLossRatePerMinute * dtMinutes
    )
```

Use actual elapsed match-clock time.

Do not decrement Energy on a fixed "every seven minutes" timer.

Only players on the pitch consume match Energy.

Unused substitutes do not.

A substitute begins at his persisted Energy and starts accumulating fatigue only after entering.

At full time:

```text
Player.energy = round(liveEnergy)
```

Persist `recentLoad` separately as defined below.

```text
    - 0.28

```

Examples:

```text
Energy 100 → 1.000
Energy  90 → 0.987
Energy  82 → 0.972
Energy  75 → 0.957
Energy  70 → 0.945
Energy  60 → 0.919
Energy  50 → 0.890
Energy  25 → 0.810
Energy   0 → 0.720
```

Continue applying readiness exactly once:

```text
usableRawAttribute =
    rawAttribute
    * positionFit

```

Do not add an additional generic "tired team" multiplier later.

The gradual curve ensures in-match fatigue matters before the player becomes catastrophically exhausted.

# 9. Persistent recent workload

`recentLoad` is not Energy and is not shown numerically to players.

It represents accumulated recent match exposure.

A neutral full 90-minute midfield appearance produces approximately:

```text
matchLoad = 1.0
```

## 9.1 Workload accumulated during a match

Initialize:

```text
currentMatchLoad = 0
```

For each elapsed match segment:

```text
loadIncrement =
    (dtMinutes / 90)
    * roleLoad
    * pressFactor
    * involvementFactor
```

Do **not** multiply workload by:

```text
age
physicalSkill
current Energy
```

Those describe the player's capacity, not the external work performed.

At full time:

```text
recentLoad =
    min(
        6.0,
        recentLoad + currentMatchLoad
    )
```

Practice matches use the same workload equation.

---

## 9.2 Exponential workload decay

On every successful game-day advance, before Energy recovery:

```text
workloadHalfLifeDays =
    matchSpacingDays
    * workloadHalfLifeMatchSpacingMultiplier
```

Version 1 therefore gives:

```text
workloadHalfLifeDays = matchSpacingDays
```

With the current schedule:

```text
matchSpacingDays = 2
workload half-life = 2 game-days
```

Decay:

```text
recentLoadNext =
    recentLoad
    * 2^(-1 / workloadHalfLifeDays)
```

For multi-day administrative catch-up, apply in one expression:

```text
recentLoadAfterN =
    recentLoadBefore
    * 2^(-N / workloadHalfLifeDays)
```

Do not loop and accumulate floating-point drift unnecessarily.

This scaling is intentional:

- if the competition cadence changes, the workload memory automatically changes in the same competitive units;
- skipping one scheduled match doubles the ordinary recovery interval and therefore causes substantially more workload decay.

---

# 10. Daily Energy recovery

Recovery occurs exactly once for each successful `advanceGameDay()`.

First decay `recentLoad`, then recover Energy.

## 10.1 Physical recovery factor

```text
physicalRecoveryFactor =
    exp(
        0.10
        * (physicalSkill - 50) / 50
    )
```

Approximate range:

```text
physicalSkill 0   → 0.905
physicalSkill 50  → 1.000
physicalSkill 100 → 1.105
```

---

## 10.2 Age recovery factor

```text
ageRecoveryYears =
    max(0, age - 27)

ageRecoveryFactor =
    exp(
        -0.0025
        * ageRecoveryYears^1.6
    )
```

Older players recover progressively more slowly.

Do not add a separate young-player bonus. Youth/prime players already receive the full `1.0` factor.

---

## 10.3 Workload recovery factor

Use a saturating nonlinear penalty:

```text
workloadRecoveryFactor =
    1
    /
    (
        1
        + 0.80 * recentLoad^2
    )
```

This is the key mechanism that distinguishes:

```text
low Energy from today's match
```

from:

```text
low Energy plus accumulated recent matches
```

The same Energy deficit recovers faster when recentLoad is low.

---

## 10.4 Recovery amount

```text
recovery =
    config.energy.recoveryScale
    * (
        11
        * physicalRecoveryFactor
        * ageRecoveryFactor
        * workloadRecoveryFactor

        + 0.02 * (100 - energy)
      )
```

Then:

```text
energyNext =
    min(
        recoveryCeiling,
        energy + recovery
    )
```

Normally:

```text
recoveryCeiling = 100
```

An injured player's ceiling is defined in Section 16.

Remove:

```text
random weekly +0..5 Energy
```

There must be no random recovery bonus.

Remove:

```text
season rollover → Energy = 100
```

The seven no-fixture gap game-days, including both the post-match buffer and
the inter-season / preparation window, naturally recover Energy and decay
workload.

# 12. Real-world injury calibration basis

Use real football data to anchor incidence, congestion, age, and severity shape, but do not copy real calendar durations directly.

The calibration basis is:

1. UEFA Elite Club Injury Study, 18 seasons:
   - match injury incidence: about `23.8 / 1000 player-hours`
   - training injury incidence: about `3.4 / 1000 player-hours`
   - average team: about `60 matches` and `215 training sessions` per season.

2. Fixture congestion evidence:
   - league matches with <=4 recovery days showed total injury RR about `1.09` versus >=6 days;
   - muscle injury RR was about `1.32`;
   - systematic reviews support increased injury risk during congested periods but do **not** support a universal ACWR threshold.

3. Age:
   - a UEFA cohort found peak overall adjusted injury hazard around ages 29–30 with HR about `1.44` versus players <=21;
   - because this engine separately models Energy and workload, only 50% of that observational age association is used as a direct residual age effect to avoid double counting.

4. Severity:
   - common professional football diagnoses were approximately:
     - 42% mild, median absence <=7 days;
     - 56% moderate, median absence 7–28 days;
     - 2% severe, median absence >28 days.
   - match and training injury severity do not require separate distributions in Version 1.

The game remains deliberately less injury-dense than literal elite-football season totals because Footmania has a shorter competitive season.

# 13. Match injury hazard model

The existing match-simulator injury architecture remains action-connected, but replace `minutesPlayedLast72h` with `recentLoad`.

## 13.1 Eligible injury participants

For every modeled action, construct a participant set from both teams:

```text
attacking local participants
+
defending local participants
```

Use the simulator's existing formation-zone involvement/defensive involvement weights.

Do not limit injury candidates to the team in possession.

Exclude:

```text
already injured players
dismissed players
players not on the pitch
```

Normalize participant exposure weights:

```text
exposure_i =
    rawLocalInvolvement_i
    /
    Σ rawLocalInvolvement
```

Therefore:

```text
Σ exposure_i = 1
```

---

## 13.2 Acute Energy injury multiplier

```text
acuteScore =
    clamp(
        ((100 - liveEnergy) / 50)^2,
        0,
        2
    )

acuteFactor =
    exp(
        ln(1.60)
        * acuteScore
    )
```

Properties:

```text
Energy 100 → 1.00
Energy  75 → ~1.13
Energy  50 → 1.60
very low Energy → capped near 2.56
```

Fatigue affects injury **probability only**.

It must not affect injury severity.

---

## 13.3 Recent workload injury multiplier

```text
loadFactor =
    exp(
        ln(1.25)
        * clamp(recentLoad, 0, 2)
    )
```

Properties:

```text
recentLoad 0.0 → 1.00
recentLoad 0.5 → 1.12
recentLoad 1.0 → 1.25
recentLoad 1.5 → 1.40
recentLoad 2.0 → 1.56
```

This produces a smooth congestion effect rather than a threshold such as "three matches in seven days."

---

## 13.4 Direct age injury multiplier

Derive the observational per-year log hazard:

```text
observedAgeBeta =
    ln(1.44)
    /
    (29.5 - 21)
```

Then keep only the residual half:

```text
ageBeta =
    observedAgeBeta * 0.50
```

Numerically:

```text
ageBeta ≈ 0.02144
```

Use:

```text
ageFactor =
    clamp(
        exp(
            ageBeta
            * (age - 26)
        ),
        0.85,
        1.45
    )
```

Approximate behavior:

```text
age 21 → ~0.90
age 26 → 1.00
age 30 → ~1.09
age 35 → ~1.21
age 38 → ~1.29
```

Do not additionally add another arbitrary "old player injury bonus."

---

## 13.5 Action/contact multiplier

Use raw action factors from model data.

If the resolved action outcome is `FOUL`, use the `FOUL` factor.

Otherwise use the modeled action/failure factor.

Precompute:

```text
meanRawActionRisk
```

from the neutral empirical action/outcome distribution in `football-baseline.json`.

Then:

```text
actionFactor =
    rawActionRisk
    /
    meanRawActionRisk
```

This guarantees the neutral empirical mean action factor is exactly `1.0`.

Do not make these action coefficients config tunables.

---

## 13.6 Base hazard calibration

Define the ordinary managed-player reference:

```text
referenceEnergy = 92
referenceRecentLoad = 0.75
referenceAge = 26
referenceActionFactor = 1
```

Compute:

```text
referenceRisk =
    acuteFactor(referenceEnergy)
    * loadFactor(referenceRecentLoad)
    * ageFactor(referenceAge)
```

Let:

```text
expectedActionsPerMatch =
    2
    * validation.reference["TEAM_MATCH.modeledActions"].mean
```

Then:

```text
baseHazardPerAction =
    config.injuries.matchTargetPerMatch
    /
    (
        expectedActionsPerMatch
        * referenceRisk
    )
```

For participant `i`:

```text
lambda_i =
    baseHazardPerAction
    * exposure_i
    * actionFactor
    * acuteFactor_i
    * loadFactor_i
    * ageFactor_i
```

Total action hazard:

```text
lambdaAction =
    Σ lambda_i
```

Probability that this action creates one injury event:

```text
P(injury on action) =
    1 - exp(-lambdaAction)
```

If an injury occurs, choose the player with:

```text
P(player i | injury) =
    lambda_i
    /
    lambdaAction
```

Then generate severity independently.

Do not perform a second aggregate injury lottery.

Multiple injuries in one match remain naturally possible across different actions.

A player removed injured cannot be injured again in the same match.

# 14. Training injuries

Training injuries are modeled as a club-level Poisson process because Footmania does not simulate every training session.

This avoids inventing dozens of training-session parameters.

## 14.1 Eligible training days

For a season:

```text
trainingEligibleDays =
    seasonDays
    - roundsPerSeason
```

A scheduled league-match game-day is not a training-injury day for that club.

Inter-season game-days **are** training-injury days.

With the current calendar:

```text
trainingEligibleDays = 35 - 14 = 21
```

---

## 14.2 Eligible players

Include:

```text
healthy senior players currently at the club
healthy loaned-in players
healthy academy players
suspended players
```

Exclude:

```text
currently injured players
loaned-out players from the parent club
players not belonging to an active pyramid club
```

A loaned-out player belongs to the host club's training-risk pool, never both clubs.

---

## 14.3 Player training-risk weight

Training has no acute in-match Energy component.

For eligible player `i`:

```text
trainingRisk_i =
    loadFactor(recentLoad_i)
    * ageFactor(age_i)
```

Reference:

```text
trainingReferenceRisk =
    loadFactor(0.50)
    * ageFactor(26)
```

Club mean relative risk:

```text
meanTrainingRelativeRisk =
    mean(trainingRisk_i)
    /
    trainingReferenceRisk
```

---

## 14.4 Daily club Poisson rate

```text
lambdaClubTrainingDay =
    (
        config.injuries.trainingTargetPerClubSeason
        /
        trainingEligibleDays
    )
    * meanTrainingRelativeRisk
```

Draw:

```text
N ~ Poisson(lambdaClubTrainingDay)
```

For each training injury event:

1. select a healthy eligible player with probability proportional to `trainingRisk_i`;
2. remove that player from the same-day candidate pool;
3. generate injury severity with the exact same severity model as match injuries.

If no eligible players exist, generate zero injuries and do not carry unused probability forward.

This gives a neutral expected value of:

```text
1.5 training injuries / club / season
```

regardless of season length.

If the season structure changes, the per-day probability automatically changes.

# 15. Injury severity model

Fatigue and recentLoad determine **whether** an injury happens.

They must not determine **how severe** it is.

Severity uses a heavy-tailed mixture grounded in professional-football absence patterns.

Use the server's deterministic seeded RNG.

## 15.1 Severity class

Draw:

```text
U ~ Uniform(0,1)
```

Class:

```text
U < 0.42:
    MINOR

0.42 <= U < 0.98:
    MODERATE

U >= 0.98:
    SEVERE
```

---

## 15.2 Minor injury

```text
B ~ Beta(2,2)

baseEquivalentRealDays =
    1
    + 6 * B
```

Range:

```text
1–7 equivalent real days
```

Mean:

```text
4 days
```

---

## 15.3 Moderate injury

```text
B ~ Beta(2,2)

baseEquivalentRealDays =
    8
    + 20 * B
```

Range:

```text
8–28 equivalent real days
```

Mean:

```text
18 days
```

---

## 15.4 Severe injury

Draw:

```text
X ~ LogNormal(
    mu = ln(60),
    sigma = 0.75
)
```

Then:

```text
baseEquivalentRealDays =
    clamp(
        X,
        29,
        365
    )
```

This creates a genuine long tail:

- many serious injuries around 1–3 months equivalent;
- rare very long absences;
- no arbitrary +20/+40/+70 bonus lottery.

---

## 15.5 Small age effect on severity

Age affects severity only slightly:

```text
severityAgeFactor =
    clamp(
        exp(
            0.008
            * (age - 27)
        ),
        0.92,
        1.12
    )
```

Therefore young players are modestly favored and old players modestly penalized.

Do not use Energy, recentLoad, pressing, or match minute here.

Final equivalent real duration:

```text
equivalentRealDays =
    baseEquivalentRealDays
    * severityAgeFactor
    * config.injuries.severityScale
```

Persist this value for reproducibility/audit.

---

# 16. Convert severity to Footmania game-days

Do not copy real football layoff days literally.

Scale injury absence to the length of Footmania's competitive season.

Empirical reference:

```text
reference professional season matches = 60
reference average competitive match spacing = 5 days
```

Therefore a real-world equivalent absence corresponds to:

```text
referenceMatchesMissed =
    equivalentRealDays
    / 5
```

Preserve the same fraction of a reference 60-match season:

```text
footmaniaMatchesMissedEquivalent =
    referenceMatchesMissed
    * (
        roundsPerSeason
        / 60
      )
```

Convert to current game-day cadence:

```text
injuryGameDays =
    max(
        1,
        ceil(
            footmaniaMatchesMissedEquivalent
            * matchSpacingDays
        )
    )
```

Equivalent compact formula:

```text
injuryGameDays =
    max(
        1,
        ceil(
            equivalentRealDays
            / 5
            * roundsPerSeason / 60
            * matchSpacingDays
        )
    )
```

This is the authoritative scaling algorithm.

It intentionally uses:

```text
roundsPerSeason
matchSpacingDays
```

rather than an arbitrary fixed 30-day or 35-day season assumption.

`interseasonDays` does not make the medical injury intrinsically longer; it simply supplies additional recovery time before the next season.

With the current 14-match / two-day-spacing schedule, Version 1 produces approximately:

```text
typical minor       → 1 game-day
typical moderate    → 1–3 game-days
upper moderate      → about 3 game-days
severe median       → about 6 game-days
very severe tail    → can span much of a season
extreme rare tail   → may cross a season boundary
```

Injuries are allowed to cross season rollover.

Never reset injuries at season rollover.

# 17. Injury state and immediate match behavior

When a match injury occurs:

1. generate severity immediately;
2. calculate `injuryGameDays`;
3. persist:

```text
injuryUntilAbsoluteGameDay =
    currentAbsoluteGameDay
    + injuryGameDays

injuryInitialGameDays =
    injuryGameDays

injuryEquivalentRealDays =
    equivalentRealDays

injuryCause =
    MATCH
```

4. remove the player from the pitch immediately;
5. emit the injury commentary/event;
6. if substitutions remain, allow substitution;
7. otherwise the team continues with one fewer player.

Training injury uses the same persistence logic with:

```text
injuryCause = TRAINING
```

# 18. Energy while injured and return-to-fitness

Do not add another visible "match fitness" number.

Use Energy itself.

For an injury with initial duration `I`:

```text
severityForReturn =
    1
    - exp(
        -I
        /
        (
            3
            * matchSpacingDays
        )
      )
```

Return Energy ceiling:

```text
injuryRecoveryEnergyCeiling =
    97
    - 17 * severityForReturn
```

Approximate range:

```text
minor injury     → ceiling around mid/high 90s
moderate injury  → ceiling around high 80s / low 90s
serious injury   → ceiling can approach ~80
```

While the player remains medically unavailable, daily Energy recovery still occurs, but:

```text
recoveryCeiling =
    injuryRecoveryEnergyCeiling
```

Therefore a long-injured player does not silently become both medically unavailable and perfectly match-fit.

On the first game-day after the injury expires:

```text
recoveryCeiling = 100
```

and normal recovery resumes.

Do not create or display another rehabilitation percentage.

The player simply returns with Energy below 100 and recovers through the ordinary Energy model.

# 19. Rare lasting skill setbacks

A rare serious injury may cause a lasting skill setback.

This is separate from temporary Energy.

Use `equivalentRealDays`, not game-scaled days, so changing season structure does not alter biological severity.

## 19.1 Probability

```text
severityExcessDays =
    max(
        0,
        equivalentRealDays - 14
    )
```

Then:

```text
pSetback =
    0.20
    * (
        1
        - exp(
            -(
                severityExcessDays
                / 45
             )^1.6
          )
      )
```

Properties:

```text
<=14 equivalent days → 0%
18 days               → ~0.4%
21 days               → ~1.0%
28 days               → ~2.9%
40 days               → ~6.8%
60 days               → ~12.9%
100 days              → ~18.8%
extreme injury        → asymptotic maximum 20%
```

This is deliberately rare.

Do not use a logarithmic probability curve; this bounded nonlinear hazard has the desired behavior without exploding.

---

## 19.2 Magnitude

If the setback roll succeeds:

```text
severityIntensity =
    1
    - exp(
        -equivalentRealDays / 60
      )
```

Draw:

```text
B ~ Beta(2,3)
```

Total skill-point loss budget:

```text
lossBudget =
    0.50
    + 2.50
      * severityIntensity
      * B
```

This makes most lasting setbacks small and severe-injury setbacks occasionally larger.

---

## 19.3 Attribute allocation

For outfield players:

```text
pace      45%
physical  45%
technical 10%
```

For goalkeepers:

```text
pace         20%
physical     50%
goalkeeping  30%
```

Map semantic aliases to the existing canonical player attributes.

Do not reduce:

```text
discipline
morale
contract values
salary
```

Do not directly reduce finishing for outfield injuries in Version 1.

For each affected attribute:

```text
rawLoss =
    lossBudget
    * attributeWeight
```

If player skills are integer-valued, use seeded stochastic rounding:

```text
integerLoss =
    floor(rawLoss)
    + Bernoulli(frac(rawLoss))
```

Then:

```text
attribute =
    max(
        attributeMinimum,
        attribute - integerLoss
    )
```

Recalculate overall using the ordinary player-overall function.

---

## 19.4 Potential effect

Let:

```text
overallLoss =
    max(
        0,
        overallBefore
        - overallAfter
    )
```

Potential loss expectation:

```text
rawPotentialLoss =
    0.50 * overallLoss
```

Use the same seeded stochastic-rounding rule.

Then:

```text
potential =
    max(
        overallAfter,
        potential - roundedPotentialLoss
    )
```

This ensures a lasting setback is not always completely erased by an unchanged potential ceiling.

Do not create a permanent "injury-prone" trait in Version 1.

# 21. AI lineup rotation

The current behavior where Energy is only a final tie-breaker is insufficient.

AI must account for both current effectiveness and the future cost of overplaying a player.

Do not give AI hidden advantages.

For each lineup candidate and assigned role:

## 21.1 Current-match value

Use the existing tactical/position candidate score:

```text
baseCandidateStrength
```

Then:

```text
currentMatchValue =
    baseCandidateStrength
    * readiness(currentEnergy)
```

---

## 21.2 Projected Energy if played

Project a full-match appearance with:

```text
minutes = 90
zoneInvolvementWeight = 0.50
selected team pressing
current age
current physicalSkill
current Energy
```

using the exact Energy formula.

Project:

```text
projectedMatchLoad
```

using the exact workload formula.

Then simulate workload decay + recovery analytically/deterministically until the next scheduled competitive league match.

Call the result:

```text
nextMatchEnergyIfPlayed
```

---

## 21.3 Projected Energy if rested

Repeat the same future projection with:

```text
today's match minutes = 0
today's match load = 0
```

Call:

```text
nextMatchEnergyIfRested
```

---

## 21.4 Rotation opportunity cost

```text
futureCost =
    baseCandidateStrength
    * (
        readiness(nextMatchEnergyIfRested)
        - readiness(nextMatchEnergyIfPlayed)
      )
```

Final AI selection value:

```text
aiSelectionValue =
    currentMatchValue
    - 0.45 * futureCost
```

`0.45` is a fixed Version 1 decision-horizon coefficient, not config.

This makes AI willing to rotate a tired/high-load star when the future loss outweighs today's marginal benefit, while still starting clearly superior players when appropriate.

If there is no future league fixture in the current season, set:

```text
futureCost = 0
```

because inter-season recovery follows.

4. Page RM et al. **The Effects of Fixture Congestion on Injury in Professional Male Soccer: A Systematic Review.** Sports Medicine, 2023. Supports higher injury risk in congested schedules without justifying one universal workload threshold.  
   https://pubmed.ncbi.nlm.nih.gov/36527592/

5. Ekstrand J et al. **Time before return to play for the most common injuries in professional football: a 16-year follow-up of the UEFA Elite Club Injury Study.** British Journal of Sports Medicine. The common diagnoses were approximately 42% mild, 56% moderate, and 2% severe by median absence category.  
   https://bjsm.bmj.com/content/54/7/421

6. Kristenson K et al. **Lower injury rates for newcomers to professional soccer: a prospective cohort study over 9 consecutive seasons.** American Journal of Sports Medicine. Adjusted injury hazard increased with age and peaked around ages 29–30 at HR about 1.44 versus players <=21.  
   https://pubmed.ncbi.nlm.nih.gov/23613443/

7. Sprouse B et al. **The Football Association Injury and Illness Surveillance Study.** Sports Medicine. Match injury incidence exceeded training incidence; injury severity did not require a separate match-versus-training severity model in the men's data.  
   https://pubmed.ncbi.nlm.nih.gov/33369724/

# 37. Acceptance definition

This overhaul is complete only when all of the following are true:

```text
[ ] Players see only one numeric condition metric: Energy.
[ ] No staminaCapacity is stored or displayed.
[ ] Match Energy loss is continuous and action-clock based.
[ ] Recent workload is exponentially decaying hidden state.
[ ] Recovery is deterministic and slower under accumulated workload.
[ ] Prime players naturally face rotation pressure after ~3–4 consecutive starts.
[ ] Older players naturally face rotation pressure sooner.
[ ] Sitting out a match substantially restores Energy and recent workload.
[ ] Inter-season naturally recovers players without a reset.
[ ] AI rotates based on current and projected future value.
[ ] Match injury incidence is calibrated to 0.35/match at the reference state.
[ ] Training injuries average ~1.5/club-season at reference conditions.
[ ] Match/training severity use one heavy-tailed model.
[ ] Fatigue and workload affect incidence, not severity.
[ ] Age affects severity only mildly.
[ ] Injury duration scales from derived season/cadence variables.
[ ] Injuries can cross season boundaries.
[ ] Rare severe injuries can cause lasting skill setbacks.
[ ] Injured players return with ordinary Energy below full rather than a second fitness stat.
[ ] Injury availability is based on absolute game-day semantics, not weekly decrement.
[ ] All stochastic behavior is seeded and deterministic.
[ ] All normal balance tunables live in game.config.jsonc.
[ ] No unspecified coefficients or implementation decisions remain.
```
