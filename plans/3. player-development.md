# Player Development and Decay System — Technical Specification

**Document Type:** Engine Technical Specification  
**Status:** Implementation Ready  
**Scope:** Player career development, decline, activity modifiers, persistence, simulation, and balancing  
**Out of Scope:** Training facilities, coaching quality, morale, injuries as independent modifiers, player potential systems, retirement logic

---

# 1. Purpose

This specification defines the player development and decay system for the game engine.

The system MUST produce persistent and believable player career trajectories while supporting:

- gradual player development through small periodic updates;
- individual differences between players;
- hidden variation in peak/decline age;
- gradual slowdown of growth before decline;
- accelerating decline after a player's decline age;
- reduced development caused by insufficient playing time;
- accelerated decline caused by insufficient playing time;
- controlled short-term randomness;
- deterministic simulation when using a seeded random number generator;
- fractional attribute development;
- compatibility with the existing attribute and OVR systems.

The system MUST NOT model career progression as independent random OVR changes.

Each player's career trajectory MUST emerge from persistent hidden traits combined with age, recent playing time, and bounded short-term randomness.

---

# 2. Terminology

| Term | Definition |
|---|---|
| Development Tick | One periodic execution of the player development system. |
| Decline Start Age | Hidden player-specific age at which natural positive development ends and decline begins. |
| Development Rate | Persistent multiplier controlling how quickly a player's underlying career trajectory progresses. |
| Development Volatility | Persistent player-specific value controlling short-term development randomness. |
| Activity | Normalized value from `0.0–1.0` representing recent competitive playing time. |
| Base Development | Expected development generated solely by the age/career curve. |
| Expected Development | Base development after persistent traits and playing-time modifiers. |
| Actual Development | Expected development after bounded random variation. |
| Seasonal Development | Development amount expressed in units per complete game season. |
| Fractional Development | Internal sub-integer attribute progression retained between ticks. |
| Peak/Decline Age | Synonym for `declineStartAge` within this specification. |

---

# 3. System Overview

For every development tick, the engine MUST evaluate each eligible player using the following pipeline:

```text
Player hidden development profile
            ↓
Current precise age
            ↓
Age-based career curve
            ↓
Persistent development-rate multiplier
            ↓
Recent match activity
            ↓
Growth/decline activity modifier
            ↓
Convert seasonal rate to tick rate
            ↓
Player-specific bounded random factor
            ↓
Development budget
            ↓
Existing attribute development system
            ↓
Fractional accumulation
            ↓
Updated attributes
            ↓
Recalculate OVR
```

The canonical calculation is:

```text
baseSeasonalDevelopment =
    calculateAgeCurve(player, currentAge)

careerAdjustedDevelopment =
    baseSeasonalDevelopment
    * player.developmentRate

activity =
    calculateRecentActivity(player)

activityModifier =
    calculateActivityModifier(
        careerAdjustedDevelopment,
        activity
    )

expectedSeasonalDevelopment =
    careerAdjustedDevelopment
    * activityModifier

expectedTickDevelopment =
    expectedSeasonalDevelopment
    * tickSeasonFraction

randomFactor =
    generateDevelopmentRandomFactor(player)

actualTickDevelopment =
    expectedTickDevelopment
    * randomFactor
```

`actualTickDevelopment` MUST then be passed to the attribute-development subsystem.

---

# 4. Persistent Player Development Profile

Every player MUST have the following hidden persistent fields:

```ts
interface PlayerDevelopmentProfile {
    declineStartAge: number;
    developmentRate: number;
    developmentVolatility: number;
}
```

These values MUST:

- be generated once;
- persist in storage;
- survive save/load cycles;
- never be rerolled on development ticks;
- never be rerolled at season boundaries;
- normally remain hidden from players/users.

---

# 5. Decline Start Age

## 5.1 Distribution

`declineStartAge` MUST be sampled from a truncated normal distribution.

```text
Distribution: Truncated Normal

μ = 30.0
σ = 2.0

minimum = 24.0
maximum = 38.0
```

Mathematically:

\[
D \sim TN(\mu=30,\sigma=2,24,38)
\]

where:

```text
D = declineStartAge
```

The sampled value MAY contain fractional years.

Example:

```text
29.42
31.18
27.93
```

A fractional age is preferable because it prevents excessive clustering of decline events on birthdays.

## 5.2 Expected Characteristics

Approximately:

```text
majority: 26–34
center:   ~30
<26:      rare
>34:      rare
24/38:    extreme bounds
```

The bounds MUST prevent unrealistic outliers.

---

# 6. Development Rate

## 6.1 Distribution

Each player MUST receive a persistent `developmentRate`.

First sample:

\[
X \sim Beta(5,5)
\]

Then map `X ∈ [0,1]` into:

```text
0.60 – 1.40
```

Formula:

\[
developmentRate =
0.60 + X(1.40 - 0.60)
\]

or:

\[
developmentRate = 0.60 + 0.80X
\]

## 6.2 Interpretation

```text
~0.60 = very slow career progression
~0.80 = below-average progression
~1.00 = normal progression
~1.20 = above-average progression
~1.40 = very fast progression
```

Because `Beta(5,5)` is symmetric and concentrated around `0.5`, most generated players MUST remain reasonably close to:

```text
developmentRate = 1.0
```

Extreme values SHOULD be uncommon.

## 6.3 Important Semantic Rule

`developmentRate` controls the **speed of both development and decline**.

Therefore a high-rate player:

- improves faster while young;
- moves through their decline curve faster when old.

A low-rate player:

- develops more gradually;
- also ages more gracefully.

This field MUST NOT determine the player's potential or maximum ability unless explicitly integrated with a separate potential system.

---

# 7. Development Volatility

## 7.1 Distribution

Each player MUST receive a persistent `developmentVolatility`.

Sample:

\[
V \sim Beta(2,5)
\]

Map into:

```text
0.03 – 0.20
```

Formula:

\[
developmentVolatility =
0.03 + V(0.20 - 0.03)
\]

or:

\[
developmentVolatility =
0.03 + 0.17V
\]

## 7.2 Interpretation

```text
0.03 = highly consistent development
0.08 = relatively stable
0.12 = moderately variable
0.16 = volatile
0.20 = highly volatile
```

Development volatility MUST NOT alter long-term expected development.

It only controls dispersion around the expected development rate.

# 8. Precise Player Age

Age calculations MUST use precise age rather than integer age whenever date information permits.

Preferred:

```text
currentAgeYears =
    (currentGameDate - player.dateOfBirth)
    / DAYS_PER_YEAR
```

Use:

```text
DAYS_PER_YEAR = 365.2425
```

or the existing engine-standard date conversion.

Example:

```text
DOB:        2000-08-01
Game date:  2030-02-01

Age ≈ 29.50
```

The engine MUST NOT delay all development transitions until integer birthdays if precise dates are available.

# 9. Career Curve

The career curve MUST be asymmetric.

It MUST conceptually follow:

```text
high growth
    ↓
moderate growth
    ↓
slow growth
    ↓
near plateau
    ↓
initial decline
    ↓
accelerating decline
```

A symmetric normal/bell curve MUST NOT be used as the complete career trajectory.

---

# 10. Pre-Decline Growth Function

Let:

```text
A = currentAge
D = declineStartAge
```

When:

```text
A < D
```

the result SHOULD be positive.

The implementation SHOULD use a normalized progress-to-decline value:

\[
p = clamp\left(
\frac{A - G_{start}}
{D - G_{start}},
0,
1
\right)
\]

Where:

```text
G_start = configured full-development reference age
```

Initial recommended value:

```text
G_start = 18
```

The recommended growth curve is:

\[
Growth(A,D) =
G_{max}(1-p)^{G_{exp}}
\]

Initial configuration:

```text
G_max = 3.0 OVR-equivalent units / season
G_exp = 1.35
```

Therefore:

```text
baseDevelopment = +Growth(A,D)
```

This produces:

- stronger development at young ages;
- progressively slower growth near peak;
- smooth convergence toward zero.

The exact values MUST remain configurable.

---

# 11. Decline Function

When:

```text
A >= D
```

define:

\[
t = A-D
\]

where `t` is years since decline began.

The decline function MUST accelerate non-linearly.

Recommended form:

\[
Decline(t) =
C_0 +
C_1t^{C_{exp}}
\]

Initial configuration:

```text
C0 = 0.30
C1 ≈ 0.37
Cexp = 1.5
```

Then:

```text
baseDevelopment = -Decline(t)
```

The target balancing profile is approximately:

| Years Since Decline | Seasonal Base Change |
|---:|---:|
| 0 | -0.3 |
| 1 | ~-0.6 |
| 2 | ~-1.0 |
| 3 | ~-1.5 |
| 4 | ~-2.2 |
| 5 | ~-2.8 |
| 6 | ~-3.6 |

These values are balancing targets rather than required exact outputs.

The function MUST be continuous enough that crossing `declineStartAge` does not cause an extreme discontinuity.

---

# 12. Development Tick Frequency

Player development MUST occur incrementally.

A complete season lasts approximately:

```text
~1 month real-world time
```

with matches approximately:

```text
every 2 real-world days
```

The preferred implementation is:

```text
1 development tick per game-world development cycle
```

If the current engine runs one daily world update, a daily development tick SHOULD be used.

The system MUST NOT depend on exactly 30 ticks per season.

Instead calculate:

\[
tickSeasonFraction =
\frac{elapsedGameTime}
{seasonDuration}
\]

or an equivalent engine-supported value.

Example:

```text
30 equal development ticks:

tickSeasonFraction = 1 / 30
```

If:

```text
seasonalDevelopment = +2.0
```

then:

```text
expected base tick ≈ +0.06667
```

before modifiers.

This ensures development remains consistent if simulation timing changes.

---

# 13. Recent Match Activity

The player's recent competitive activity MUST be based on the last five eligible team matches.

Default weights:

```ts
const ACTIVITY_WEIGHTS = [
    1.00,
    0.75,
    0.55,
    0.40,
    0.30,
];
```

Index `0` represents the most recent match.

For each match:

\[
minutesRatio_i =
clamp\left(
\frac{minutesPlayed_i}
{regulationMinutes_i},
0,
1
\right)
\]

Normally:

```text
regulationMinutes = 90
```

Then:

\[
Activity =
\frac{
\sum_i w_i \times minutesRatio_i
}{
\sum_i w_i
}
\]

The result MUST satisfy:

```text
0.0 <= activity <= 1.0
```

---

# 14. Activity Examples

Using five complete matches:

### Player starts every match

```text
90 / 90 / 90 / 90 / 90

activity = 1.00
```

### Player plays half of every match

```text
45 / 45 / 45 / 45 / 45

activity = 0.50
```

### Player misses the latest match but started the previous four

```text
0 / 90 / 90 / 90 / 90

activity ≈ 0.67
```

Because the latest match carries the largest weight, recent inactivity MUST affect the score more strongly than older inactivity.

---

# 15. Eligible Match History

The engine MUST NOT treat unavailable historical matches as missed matches.

A historical match is eligible only if the player:

- existed in the game world;
- belonged to the relevant team at that time, or player participation history is globally preserved;
- was eligible for activity tracking under the game's roster model.

Therefore:

```text
2 eligible matches available
```

means the denominator MUST contain only those two match weights.

It MUST NOT implicitly append three zero-minute matches.

---

# 16. Growth Activity Modifier

If:

```text
careerAdjustedDevelopment > 0
```

use:

\[
GrowthModifier =
0.65 + 0.35A
\]

where:

```text
A = activity
```

Therefore:

| Activity | Growth Multiplier |
|---:|---:|
| 1.00 | 1.000 |
| 0.75 | 0.9125 |
| 0.50 | 0.8250 |
| 0.25 | 0.7375 |
| 0.00 | 0.6500 |

Young players MUST therefore retain some natural development even with no competitive playing time.

Inactivity alone MUST NOT normally convert positive age-driven growth into negative development.

---

# 17. Decline Activity Modifier

If:

```text
careerAdjustedDevelopment < 0
```

use:

\[
DeclineModifier =
1 + 0.40(1-A)
\]

Therefore:

| Activity | Decline Multiplier |
|---:|---:|
| 1.00 | 1.00 |
| 0.75 | 1.10 |
| 0.50 | 1.20 |
| 0.25 | 1.30 |
| 0.00 | 1.40 |

Playing regularly therefore slows the **relative rate of deterioration caused by inactivity**, but MUST NOT eliminate natural aging.

A fully active declining player still receives:

```text
100% of their natural decline
```

---

# 18. Plateau Behavior

If:

```text
abs(careerAdjustedDevelopment) < DEVELOPMENT_EPSILON
```

the activity modifier SHOULD be:

```text
1.0
```

Recommended:

```text
DEVELOPMENT_EPSILON = 0.000001
```

Activity alone SHOULD NOT cause meaningful development or decline when the age curve itself evaluates to zero.

---

# 19. Tick Randomness

Each development tick MUST use multiplicative random noise.

The random factor MUST be generated from a truncated normal distribution.

For player `P`:

\[
R \sim TN(
\mu=1.0,
\sigma=P.developmentVolatility,
0.80,
1.20
)
\]

Then:

\[
ActualTick =
ExpectedTick \times R
\]

Default bounds:

```text
minimum = 0.80
maximum = 1.20
```

This means random noise:

- cannot reverse the sign of development;
- cannot create growth from decline;
- cannot create decline from growth;
- cannot exceed ±20% of expected tick magnitude.

---

# 20. Random Sampling Requirements

The engine MUST use its deterministic seeded RNG abstraction if one exists.

It MUST NOT use uncontrolled global randomness such as:

```ts
Math.random()
```

directly inside simulation logic if deterministic simulation is supported elsewhere.

Recommended interface:

```ts
interface RandomSource {
    uniform(): number;
    normal(mean: number, stdDev: number): number;
    truncatedNormal(
        mean: number,
        stdDev: number,
        min: number,
        max: number
    ): number;
    beta(alpha: number, beta: number): number;
}
```

If Beta sampling is not already supported, implement it centrally rather than embedding custom sampling logic in the player service.

---

# 21. Canonical Development Formula

For player `P`:

\[
B = CareerCurve(P,A)
\]

\[
C = B \times P.developmentRate
\]

Activity:

\[
M =
\begin{cases}
0.65 + 0.35A_c, & C > 0 \\
1 + 0.40(1-A_c), & C < 0 \\
1, & C = 0
\end{cases}
\]

where:

```text
Ac = recent activity
```

Expected seasonal development:

\[
E_s = C \times M
\]

Expected development during the tick:

\[
E_t = E_s \times F_t
\]

where:

```text
Ft = fraction of one season represented by this tick
```

Random factor:

\[
R \sim TN(1,P.volatility,0.8,1.2)
\]

Final tick budget:

\[
\boxed{
DevelopmentTick =
B
\times developmentRate
\times activityModifier
\times tickSeasonFraction
\times randomFactor
}
\]

---

# 22. Reference Pseudocode

```ts
function calculateDevelopmentTick(
    player: Player,
    context: DevelopmentContext,
): number {
    const age = calculatePreciseAge(
        player.dateOfBirth,
        context.currentDate,
    );

    const baseSeasonalDevelopment =
        calculateAgeDevelopment(
            age,
            player.developmentProfile.declineStartAge,
        );

    if (
        Math.abs(baseSeasonalDevelopment)
        < config.developmentEpsilon
    ) {
        return 0;
    }

    const careerAdjusted =
        baseSeasonalDevelopment
        * player.developmentProfile.developmentRate;

    const activity =
        calculateRecentActivity(
            player,
            context.recentMatches,
        );

    const activityModifier =
        careerAdjusted > 0
            ? calculateGrowthActivityModifier(activity)
            : calculateDeclineActivityModifier(activity);

    const expectedTick =
        careerAdjusted
        * activityModifier
        * context.tickSeasonFraction;

    const randomFactor =
        rng.truncatedNormal(
            1.0,
            player.developmentProfile.developmentVolatility,
            config.randomFactor.min,
            config.randomFactor.max,
        );

    return expectedTick * randomFactor;
}
```

# 23. Attribute Application

If OVR is derived from player attributes, the engine MUST NOT directly modify OVR.

The tick result MUST instead represent a development budget.

Example:

```text
actualTickDevelopment = +0.052
```

The existing attribute progression system SHOULD distribute this budget across applicable attributes.

For negative values:

```text
actualTickDevelopment = -0.071
```

the decline system SHOULD distribute deterioration across applicable attributes.

After attributes are updated:

```text
OVR = calculateOverall(attributes)
```

MUST be executed through the existing OVR mechanism.

---

# 24. Fractional Attribute Development

The engine MUST retain fractional progress.

Integer truncation per tick is prohibited.

Valid approaches include:

### Floating-point attributes internally

```text
finishingInternal = 74.383
displayedFinishing = 74
```

or:

### Separate progress accumulators

```text
finishing = 74
finishingProgress = 0.383
```

When progress crosses an integer threshold:

```text
74 + 1.034
```

becomes:

```text
finishing = 75
progress = 0.034
```

Negative fractional progress MUST behave equivalently.

# 25. Development Profile Generation

When a new player is created:

```ts
function generateDevelopmentProfile(
    rng: RandomSource,
): PlayerDevelopmentProfile {
    const declineStartAge =
        rng.truncatedNormal(
            30,
            2,
            24,
            38,
        );

    const developmentRateRaw =
        rng.beta(5, 5);

    const developmentRate =
        lerp(
            0.60,
            1.40,
            developmentRateRaw,
        );

    const volatilityRaw =
        rng.beta(2, 5);

    const developmentVolatility =
        lerp(
            0.03,
            0.20,
            volatilityRaw,
        );

    return {
        declineStartAge,
        developmentRate,
        developmentVolatility,
    };
}
```

# 27. Existing Player Migration

Existing players MUST receive development profiles without changing their current ability.

Migration MUST:

1. add the required persistent fields;
2. generate a valid decline age;
3. generate development rate;
4. generate volatility;
5. save those values;
6. leave current attributes and OVR unchanged.

Where possible, backfill generation SHOULD be deterministic.

Recommended seed derivation:

```text
hash(
    worldSeed,
    playerId,
    "development-profile-v1"
)
```

This ensures identical databases/world seeds produce consistent profiles.

# 28. Transfers

Recent activity SHOULD follow the player across transfers if global match participation data is available.

If the architecture only exposes team-local history, transferred players MUST NOT be initialized as fully inactive.

Fallback:

```text
activity = configured neutralTransferActivity
```

Recommended initial value:

```text
neutralTransferActivity = 0.70
```

This fallback SHOULD only persist until sufficient valid match history exists.

---

# 29. New Players

New players without historical matches MUST NOT receive inactivity penalties due solely to missing data.

Recommended behavior:

```text
if eligibleMatchCount == 0:
    activity = DEFAULT_ACTIVITY
```

Initial recommendation:

```text
DEFAULT_ACTIVITY = 0.70
```

As real match data accumulates, the synthetic default MUST be removed from the calculation.

---

# 30. Injuries

For version 1, injury absence SHOULD naturally reduce activity because the player receives fewer competitive minutes.

No injury-specific exemption is required.

However, the activity subsystem MUST NOT encode reasons for absence directly.

Future systems MAY add independent modifiers:

```text
trainingModifier
injuryRecoveryModifier
moraleModifier
coachModifier
facilityModifier
```

These MUST be composable without redesigning the career curve.

# 33. Activity Calculation Pseudocode

```ts
function calculateRecentActivity(
    player: Player,
    matches: Match[],
): number {
    const eligibleMatches =
        getEligibleRecentMatches(
            player,
            matches,
            config.activity.weights.length,
        );

    if (eligibleMatches.length === 0) {
        return config.activity.defaultActivity;
    }

    let weightedMinutes = 0;
    let totalWeight = 0;

    for (
        let i = 0;
        i < eligibleMatches.length;
        i++
    ) {
        const match = eligibleMatches[i];
        const weight = config.activity.weights[i];

        const minutesPlayed =
            getPlayerMinutes(player, match);

        const ratio = clamp(
            minutesPlayed / match.regulationMinutes,
            0,
            1,
        );

        weightedMinutes += ratio * weight;
        totalWeight += weight;
    }

    return weightedMinutes / totalWeight;
}
```

# 34. Growth Activity Function

```ts
function calculateGrowthActivityModifier(
    activity: number,
): number {
    const min =
        config.activity.inactiveGrowthMultiplier;

    return min + (1 - min) * clamp(activity, 0, 1);
}
```

With default configuration:

```text
0.65 + 0.35 × activity
```

---

# 35. Decline Activity Function

```ts
function calculateDeclineActivityModifier(
    activity: number,
): number {
    const max =
        config.activity.inactiveDeclineMultiplier;

    return 1 + (max - 1)
        * (1 - clamp(activity, 0, 1));
}
```

With default configuration:

```text
1 + 0.40 × (1 - activity)
```

# 36. Sign Invariance

The development randomness system MUST preserve the sign of the expected development result.

Given:

```text
expectedTick > 0
```

then:

```text
actualTick >= 0
```

Given:

```text
expectedTick < 0
```

then:

```text
actualTick <= 0
```

The configured random-factor minimum MUST therefore remain greater than zero.

With:

```text
randomFactor ∈ [0.80, 1.20]
```

this invariant is guaranteed.

---

# 37. Development Caps

Existing player attribute minimums and maximums MUST remain authoritative.

Example:

```text
attribute minimum = 1
attribute maximum = 99
```

The development subsystem MUST NOT exceed them.

Any unused positive or negative development budget caused by attribute caps SHOULD follow the behavior of the existing attribute progression system.

Do not silently modify the configured attribute range.

---

# 38. Tick Idempotency

A development tick MUST NOT be applied twice for the same logical period.

If the engine uses scheduled jobs, persisted world ticks, or resumable simulation, development execution SHOULD be tied to a unique simulation time identifier.

Example:

```text
developmentTickId =
    worldId + simulationDate
```

or equivalent.

Restarting the server MUST NOT accidentally award duplicate development.

---

# 39. Performance Requirements

The development system SHOULD be approximately:

```text
O(players × recentMatchWindow)
```

Since:

```text
recentMatchWindow = 5
```

activity calculation is effectively constant-time per player when appropriate indices/history structures exist.

The implementation SHOULD NOT scan an entire career's match history for every tick.

Match participation SHOULD be queried/indexed efficiently.

---

# 40. Statistical Tests — Decline Age

Generate at least:

```text
100,000 profiles
```

and validate:

- all values are within `[24, 38]`;
- sample mean is approximately `30`;
- distribution is centered near `30`;
- extreme values are uncommon;

# 49. Balancing Acceptance Criteria

Initial implementation SHOULD satisfy the following qualitative outcomes:

### Young player, active

Develops close to their natural career rate.

### Young player, inactive

Still develops, but meaningfully slower.

### Player approaching decline age

Growth becomes small before decline begins.

### Newly declining player

Decline begins gently.

### Older veteran

Decline accelerates with increasing years past their decline age.

### Active veteran

Still declines.

### Inactive veteran

Declines substantially faster.

### Same-age players

Can have materially different trajectories because of:

- decline age;
- development rate;
- volatility;
- activity.

### Repeated simulation

Should produce variety without making player careers appear random or chaotic.

# 50. Prohibited Behaviors

The implementation MUST NOT:

- reroll `declineStartAge`;
- reroll `developmentRate`;
- reroll `developmentVolatility`;
- use a normal curve as the complete player career curve;
- make development an independent random walk;
- directly modify OVR when OVR is attribute-derived;
- discard fractional development every tick;
- treat unknown match history as inactivity;
- let one missed match create a major development change;
- allow activity to completely stop natural veteran decline;
- make inactivity alone cause normal young players to decline;
- use unbounded random development;
- let normal random noise change development direction;
- scatter balancing constants throughout the codebase;
- create duplicate development systems alongside existing attribute progression logic;
- apply the same logical development tick twice.
