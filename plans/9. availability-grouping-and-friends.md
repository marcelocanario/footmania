# Plan 9 — UTC availability, window-overlap grouping, friend consent & friends tab

Supersedes the timezone-based parts of `plans/1. multiplayer.md` (§36 clustering,
timezone capture/update) and `plans/8. promotion-relegation-elo-rebalancing.md`
(§30-§37 objective order) as implemented. Historical plan text is left intact;
this document records the current behavior and its rationale.

## 1. The server is pure UTC

- The server never asks for, stores (new rows), or interprets a timezone.
  `Club.timezone` remains in the database solely as a **legacy migration
  marker**; new clubs have it null.
- Preferred match times are half-hour slots on a fixed **UTC grid**
  (`0 = 00:00–00:30 UTC … 47`). They feed both fixture kickoff selection
  (`game/scheduling.ts`) and division regrouping (§3).
- The client owns localization: `frontend/src/utils/time.ts` auto-detects the
  browser timezone, renders every instant browser-local, and converts preferred
  hours local⇄UTC at load/save edges. Kickoff display is consolidated there so
  all screens format identically.
- One-time migration: on world load, a club row that still carries a timezone
  has its stored slots shifted local→UTC with that zone's offset (rounded to
  the nearest slot for :45-offset zones); the marker is cleared on the next
  persist, making the conversion idempotent.

## 2. Grouping objectives (in priority order)

`buildBalancedTierGroups` (backend/src/game/multiplayer.ts):

1. **Human density** — fewest possible divisions (invariant 5).
2. **Direct friendships** — maximize co-grouped accepted friend pairs.
3. **Friends-of-friends** — tie-break on second-order connections.
4. **Window-overlap cost** — pairwise cost between two constrained clubs is
   `(slotsPerDay − |A ∩ B|)²`; any unconstrained member makes the pair cost 0
   (same convention as kickoff scheduling). Minimize the per-tier sum.
5. **Elo balance** — only among arrangements tied on 1–4 (epsilon-guarded);
   swap-improvement passes may never worsen a higher-priority objective.
6. **Seeded tie-rank** — deterministic hash of `(assignmentSeed, rotation)`.

Rotation candidates are seeded from the circular centroid of each club's
preferred windows; unconstrained clubs sort last. Rationale: overlap measures
whether two managers can actually meet inside both windows, unlike centroid
distance, which misjudges wrapped night windows.

Assignment pipeline: a deterministic branch-and-bound maximizes objectives 2–3
exactly under a fixed node budget (very large tiers fall back to
centroid-seeded rotations refined by guarded swap passes). Window-overlap and
Elo then improve through swaps that can never worsen a higher-priority
objective, so the documented priority order always holds.

## 3. Friend-grouping consent (bilateral rule)

- New per-club flag `friendGroupingOptIn` (Prisma default true; undefined =
  true for legacy in-memory rows). Settings exposes an on/off switch
  (`PUT /mp/club/friend-grouping`).
- A friendship influences objectives 2–3 **only when both owners opted in**:
  one-sided opt-out removes the pair effect entirely. This prevents pulling an
  unwilling player into someone's group (adversarial rule; covered by tests).
- Consent changes never move divisions mid-season; they apply at rollover.

## 4. Friends tab & invite links

- `POST /auth/invite` (existing) mints a single-use token; signup with the
  token auto-creates the friendship idempotently (existing behavior, now wired
  into the UI via `/login?invite=<token>`).
- `GET /auth/friends`, `DELETE /auth/friends/:userId` — list/remove own edges.
- `GET /auth/invitations`, `DELETE /auth/invitations/:token` — list/revoke own
  unused tokens; used tokens are immutable history.
- The Friends screen generates/copy-pastes links, revokes pending invitations,
  and manages the friend list.

## 5. Testing requirements

- Unit: overlap cost semantics (identical/disjoint/wrapped/unconstrained),
  objective ordering incl. friendships-before-overlap, bilateral consent
  matrix, seeded determinism.
- Persistence: consent round-trip; legacy conversion runs exactly once across
  reload/persist cycles.
- Integration: friend-grouping toggle endpoint; friends list/remove;
  invitation list/revoke; adversarial cross-user removal attempts.
