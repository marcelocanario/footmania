# Promotion, Relegation, Human Elo, and Group Rebalancing Plan

## 1. Goals

Implement three connected changes:

1. Add a persistent **human-club Elo rating** updated only from human-vs-human competitive matches.
2. Replace the current accidental cross-group ordering of promotion candidates with **Elo-based selection** after the automatic rank-1 round.
3. After all clubs have been assigned to their next-season tier, **rebuild the groups inside each tier**:
   - first try to keep friends and friends of friends together;
   - then optimize timezone proximity;
   - then, where the social and timezone quality is equivalent, balance Elo so groups have similar competitive strength.

The final hierarchy should be:

```text
Promotion:
1. Round 1: human rank within the club's group
2. Round 2 onward: Elo across all remaining eligible humans
3. Normalized standings statistics
4. clubId deterministic fallback

Group assignment:
1. Friends and friends of friends within the same target division
2. Timezone similarity
3. Elo balance
4. Random tie-breaker
```

Group assignment never crosses a target division. Promotions and relegations
must be finalized before group assignment begins.

AI filler clubs remain participants in matches and standings but are completely excluded from:

```text
Elo
promotion eligibility
relegation eligibility where current human-only rules apply
cross-group promotion comparison
social/timezone/Elo group balancing
```

AI fillers are inserted only after humans have been assigned to their next-season groups.

---

## 2. Important architectural change: promotion belongs to the tier, not the destination group

Today `computeNextTierAssignments` appears to reason primarily through parent/child group relationships.

Once we introduce **post-rollover group rebalancing**, a promoted club no longer really belongs to a particular parent group.

Therefore split the concept into:

```text
Step 1: determine TARGET TIER
Step 2: determine GROUP inside that tier
```

Do not directly decide:

```text
3.1 → 2.1
```

during promotion selection.

Decide:

```text
Club X:
currentTier = 3
nextTier = 2
```

Then, after every promotion/relegation/stay decision has been completed:

```text
rebalance all Tier 2 human clubs into:
2.1
2.2
...
```

This is important because otherwise the existing tree structure would continue artificially constraining promotion.

## 3. Human Elo data model

Add persistent Elo to the **club**, not the user account.

A user can change clubs over the lifetime of the game, and Elo is intended to represent the competitive history of the club/team.

Add:

```text
club.eloRating
club.eloRatedMatches
```

Initial values:

```text
eloRating       = 1500.0
eloRatedMatches = 0
```

Use floating-point internally.

If Elo is displayed in internal tooling, round it for display:

```text
displayElo = round(eloRating)
```

Never use the rounded value for calculations.
Elo is not displayed to regular users.

Example:

```text
stored: 1538.427
displayed: 1538
```

## 4. Which matches affect Elo

A match is Elo-rated only if all of the following are true:

```text
home club is human-controlled
away club is human-controlled
match is an official senior competitive match
match completed normally
```

Included:

```text
league matches
official competitive cup matches, if/when applicable
```

Excluded:

```text
human vs AI
AI vs AI
friendlies
test matches
preseason/exhibition matches
youth matches
abandoned/unplayed fixtures
administrative placeholder results that were never simulated
```

Using official cup matches is desirable because it creates additional connections between otherwise isolated groups.

### Human status must be captured at match time

Do not determine Elo eligibility later from the club's current ownership.

When the match starts/finalizes, persist or determine:

```text
homeWasHuman
awayWasHuman
```

Elo eligibility is based on that state.

This avoids historical Elo changing conceptually if a club later becomes inactive or AI-controlled.

## 5. Elo formula

Use standard Elo expected score.

Constants:

```text
ELO_INITIAL = 1500
ELO_SCALE   = 400
ELO_K       = 24
ELO_HOME_ADVANTAGE = 60
```

The home advantage exists because the match simulator already gives the home club a real advantage. Without compensating for it, Elo would systematically over-reward expected home victories.

For home club `H` and away club `A`:

```text
adjustedHomeRating = eloH + 60
adjustedAwayRating = eloA
```

Expected home result:

```text
EH = 1 / (1 + 10 ^ ((eloA - adjustedHomeRating) / 400))
```

Expected away result:

```text
EA = 1 - EH
```

Actual result:

```text
home win:
SH = 1.0
SA = 0.0

draw:
SH = 0.5
SA = 0.5

away win:
SH = 0.0
SA = 1.0
```

Updates:

```text
deltaH = 24 × (SH - EH)
deltaA = 24 × (SA - EA)

newEloH = eloH + deltaH
newEloA = eloA + deltaA
```

Because:

```text
deltaH + deltaA = 0
```

every rated match is zero-sum.

## 6. Draws against stronger teams

This naturally satisfies the requirement that drawing a stronger club should benefit the weaker club.

Example:

```text
Home team Elo = 1400
Away team Elo = 1600
```

Adjusted home rating:

```text
1460
```

Expected home score:

```text
EH ≈ 0.309
```

If the match is a draw:

```text
SH = 0.5
```

Then:

```text
deltaH = 24 × (0.5 - 0.309)
       ≈ +4.58
```

So:

```text
1400 → 1404.58
```

The stronger club loses the same amount:

```text
1600 → 1595.42
```

Likewise, a very surprising draw produces a larger adjustment than a draw between equally rated clubs.

No special "draw bonus" needs to exist.

---

## 7. Do not use goal difference in Elo

Do not multiply Elo changes based on winning margin.

A:

```text
1-0 victory
```

and:

```text
5-0 victory
```

produce the same Elo result.

Reasons:

- prevents score-running exploits;
- avoids double-counting match-engine randomness;
- makes Elo measure results rather than goal farming;
- promotion still considers league performance separately.

---

## 8. Elo updates must be atomic

When a human-human match completes:

1. Read both pre-match Elo values.
2. Calculate both expected results from those same values.
3. Calculate both deltas.
4. Write both new ratings in one transaction.
5. Increment both `eloRatedMatches`.
6. Mark the match as having had Elo processed.

Add something equivalent to:

```text
match.eloProcessed = true
```

This makes match finalization idempotent.

If the finalize operation accidentally runs twice:

```text
if eloProcessed:
    do not update Elo again
```

Create an Elo history/event record:

```text
ClubEloEvent
```

Fields:

```text
id
matchId
clubId
opponentClubId

ratingBefore
ratingAfter
delta

expectedScore
actualScore

createdAt
```

There should be two records for every Elo-rated match.

This provides:

- auditability;
- debugging;
- future Elo chart;
- ability to detect accidental double updates.

Add a unique constraint equivalent to:

```text
(matchId, clubId)
```

## 10. Seasonal Elo regression

Elo should not preserve historical strength forever.

At rollover, after promotion decisions have used the final-season ratings, regress each human club slightly toward 1500.

Use:

```text
ELO_SEASON_RETENTION = 0.90
```

Formula:

```text
newElo =
    1500
    + 0.90 × (oldElo - 1500)
```

Examples:

```text
1700 → 1680
1600 → 1590
1500 → 1500
1400 → 1410
1300 → 1320
```

This is deliberately mild.

It:

- preserves most information;
- gradually removes obsolete history;
- helps reconnect rating pools;
- prevents founding clubs from retaining permanent Elo advantages.

Do **not** reset Elo based on division.

## 11. Timing of seasonal regression and scheduled rollover

The exact order must be:

```text
FINAL MATCH DAY:
1. Complete final matches.
2. Apply their Elo updates.
3. Execute `SEASON_RESULTS_FINALIZE` and freeze final standings.

FOLLOWING GAME DAY:
4. Use FINAL PRE-REGRESSION Elo for promotion selection.
5. Determine promotions/relegations/stayers.
6. Apply 10% seasonal Elo regression.
7. Add any newly created human clubs at Elo 1500.
8. Rebalance clubs into next-season groups.
9. Generate/fill AI slots.
10. Activate next season.
```

Promotion therefore uses the ratings actually earned during the completed season.

Group balancing uses the slightly regressed next-season ratings.

The final-match processing must not perform promotions, relegations, or group
assignment immediately. It only finalizes the completed season and schedules
the rollover work for the next game-day boundary. Therefore, all promotion,
relegation, target-division, and group decisions happen on the game day after
the last match of the season.

### 11.1. Scheduler change

When all final-season fixtures are terminal, execute
`SEASON_RESULTS_FINALIZE` and schedule the inter-season rollover sequence for
the following game day. At that next boundary, the scheduler must execute, in
order:

```text
1. INTERSEASON_START
2. PROMOTION_RELEGATION
3. DIVISION_RESTRUCTURE
4. NEXT_SEASON_PREPARATION
```

`PROMOTION_RELEGATION` must complete target-tier assignments before
`DIVISION_RESTRUCTURE` builds groups. `DIVISION_RESTRUCTURE` must then apply
the same-division social, timezone, Elo, and random-seed rules from this plan.

Do not start next-season competitive fixtures before this sequence completes.
If the server is offline at the boundary, process the due rollover event on
recovery without changing its scheduled game-day meaning. The complete
sequence remains one lock-aware, retry-safe rollover operation.

## 12. Deterministic league standings

Fix the current weakness in `standingsTiebreak`.

Current:

```text
points
wins
goal difference
goals scored
```

Change to:

```text
1. points DESC
2. wins DESC
3. goalDifference DESC
4. goalsFor DESC
5. eloRating DESC (hidden)
6. clubId ASC
```

Elo is a hidden deterministic standings tie-breaker and must not be exposed to users.

The `clubId` comparison is not intended as a sporting rule.

It exists solely so every operation has an explicitly deterministic final ordering.

Do not depend on JavaScript stable sort/insertion order.

## 13. Human promotion ranking inside a group

Continue the current behavior.

For every lower-tier group:

1. Calculate the normal full standings.
2. Remove:
   - AI clubs;
   - non-ACTIVE human clubs;
   - clubs otherwise ineligible under existing rules.
3. Preserve the standings order of the remaining clubs.

Example:

```text
Overall:

1 AI
2 AI
3 Human A
4 Human B
5 AI
6 Human C
7 AI
8 Human D
```

Promotion-eligible order is:

```text
Human rank 1 = Human A
Human rank 2 = Human B
Human rank 3 = Human C
Human rank 4 = Human D
```

AI therefore never consumes a promotion position.

## 14. Missing groups

A nonexistent group has:

```text
0 promotion candidates
0 guaranteed promotion entitlement
0 effect on promotion candidate ranking
```

Do not create a fake candidate or reserve a promotion slot for it.

This is central to the edge case described.

## 15. Change promotion selection from parent-local to tier-global

For promotion from Tier `D+1` into Tier `D`, calculate the promotion vacancies across the **entire target tier**.

Example:

```text
Division 2:
2.1
2.2
```

Treat them together when deciding how many Division 3 clubs must move into Division 2.

Afterward, the regrouping algorithm decides whether a promoted club plays in:

```text
2.1
or
2.2
```

This allows the strongest remaining eligible club in Division 3 to earn the extra promotion place, even if it finished below second among humans.

## 16. Calculate promotion vacancy count

Preserve the current vacancy semantics.

For target tier `T`:

```text
promotionVacancies =
    configured human capacity of active target-tier groups
    - humans staying in target tier after relegation/abandonment
```

Do not count AI filler removal as an additional vacancy if the current model intentionally does not treat filler as human capacity.

In other words, this plan should not silently alter the existing economic/population model around filler clubs.

It only changes **which lower-tier humans fill existing promotion vacancies**.

## 18. Promotion selection algorithm

Promotion must preserve Round 1, then use an Elo-ranked pool for all later
promotion places. Round 1 consists of every eligible human rank 1 club. After
Round 1, eligible human rank 2, rank 3, and lower candidates may be compared
against one another.

Pseudo-rule:

```text
remaining = promotionVacancies

roundOneCandidates =
    all eligible clubs whose humanRank == 1

promote as many roundOneCandidates as vacancies allow,
using cross-group promotion ordering only if capacity is insufficient
remaining -= the number promoted

if remaining > 0:
    laterCandidates =
        all eligible clubs whose humanRank >= 2

    sort laterCandidates by cross-group promotion ordering
    promote the first remaining candidates
```

Round 1 preserves the automatic group-winner entitlement. From Round 2
onward, Elo is the primary criterion across all remaining eligible candidates.
A third-place human with Elo 1800 can therefore outrank an available
second-place human with Elo 1400.

Correct hierarchy:

```text
human rank 1 entitlement
THEN Elo for human ranks 2 and lower
```

---

## 19. Cross-group promotion ordering

From Round 2 onward, compare all remaining candidates with human rank 2 or
lower using:

```text
1. Elo DESC
2. pointsPerGame DESC
3. goalDifferencePerGame DESC
4. goalsForPerGame DESC
5. winsPerGame DESC
6. clubId ASC
```

Use ratios because groups may theoretically contain different numbers of fixtures.

Definitions:

```text
PPG = points / matchesPlayed

GDPerGame =
    (goalsFor - goalsAgainst) / matchesPlayed

GFPerGame =
    goalsFor / matchesPlayed

winsPerGame =
    wins / matchesPlayed
```

If:

```text
matchesPlayed == 0
```

all four normalized standings values are:

```text
0
```

Elo therefore dominates cross-group comparison.

---

## 23. Edge case: fewer vacancies than group winners

Normally the pyramid should be configured so every active group's top eligible human can move upward.

Nevertheless the algorithm must handle an inconsistent population state.

Example:

```text
3 active lower groups
2 available promotion places
```

Candidates:

```text
A1
B1
C1
```

There are only two vacancies.

Because capacity is insufficient for every Round-1 winner, apply the
cross-group ordering to the Round-1 candidates:

```text
Elo
PPG
GD/game
GF/game
wins/game
clubId
```

Promote the top two.

Do not overflow the upper division.

Log this condition as:

```text
PROMOTION_CAPACITY_CONSTRAINT
```

because it means the competition structure could not satisfy the normal "one winner per active group" expectation.

---

## 24. Edge case: more vacancies than rank-2-or-lower clubs

Example:

```text
3 active groups
7 vacancies
```

Round 1:

```text
3 winners promoted
remaining = 4
```

After Round 1, pool all eligible rank-2-or-lower humans and sort them by Elo,
then the normalized standings statistics and `clubId`. Promote the top four
from that pool.

Continue until:

```text
remaining == 0
```

or no eligible human candidates remain.

---

## 25. Edge case: not enough eligible humans

If the lower tier cannot supply enough humans:

```text
remaining > 0
```

after every human candidate has been exhausted.

Do not:

```text
promote AI
promote inactive clubs
duplicate clubs
invent clubs
```

Leave the human slot unfilled and let the existing AI/population filler logic handle the resulting competition composition.

## 26. Relegation

Do **not** use Elo for relegation.

Relegation remains determined by league performance according to the existing relegation rules.

Reason:

Elo is needed to solve an otherwise incomparable **cross-group promotion problem**.

There is no need for a high-Elo team to be protected from deserved relegation after finishing in a relegation place.

So:

```text
relegation = standings
promotion comparison = Elo across all remaining candidates after Round 1
```

## 27. Friends and game invitations

An existing player can invite another person to join the game. The invitee
signs up through that invitation, and signup immediately creates a persistent
accepted friendship between the inviter and invitee. There is no separate
friend-request flow and no separate grouping treatment for invitees versus
friends.

The grouping relationship graph is built from accepted friendships:

```text
friends      = directly connected players
friends of friends = players connected by a two-edge path
```

Only human-controlled clubs are included in this graph. AI filler clubs have
no friends and do not affect social grouping.

Friend relationships influence next-season grouping only after each club's
target division has been finalized. A friendship never keeps a club in the
wrong division and never changes promotion, relegation, or tier assignment.

Within each target division, the social objective is to maximize colocated
friend relationships, then colocated friends-of-friends relationships. Direct
friendships are considered before second-degree relationships when a tradeoff
is unavoidable. Group capacity and even human distribution remain hard
constraints.

The system should record the invitation and accepted friendship relation in an
idempotent way so retries do not create duplicate accounts, friendships, or
invitations. The friendship is created as part of the invitee signup boundary.

---

## 27.1. Group-assignment objective order

After target divisions have been determined, group assignment is lexicographic:

```text
1. maximize same-group direct friendships
2. among equivalent direct-friend arrangements, maximize same-group
   friends-of-friends relationships
3. among equivalent social arrangements, minimize timezone cost
4. among equivalent social/timezone arrangements, minimize Elo imbalance
5. break any remaining tie randomly
```

There is no cross-division social preference. A direct friend in another
division is not a candidate for the current division's grouping pool.

Generate one `groupAssignmentSeed` when the rollover begins and persist it
with the rollover/audit record. Use that seed for all random tie-breaks so a
retry reproduces the already-selected groups instead of reshuffling them.

---

## 27.2. Should Elo be used to balance new groups?

**Yes, but strictly as a tertiary objective behind social grouping and timezone.**

This is useful because otherwise geographical clustering could accidentally produce:

```text
Group A average Elo = 1640
Group B average Elo = 1470
```

That creates a persistent "group of death."

It is particularly undesirable because the new promotion algorithm uses finishing rank first. A strong club in an abnormally strong group could repeatedly finish second while a weaker club elsewhere wins its group.

However, Elo should **not** override timezone clustering.

Do not send a North American Atlantic club into a European-heavy group merely to improve Elo variance.

Elo is now the third objective, after social proximity and timezone. The
optimization order is lexicographic:

```text
1. maximize social cohesion
2. among socially equivalent arrangements, minimize timezone cost
3. among socially/timezone-equivalent arrangements, minimize Elo imbalance
4. random tie-breaker
```

Not:

```text
timezoneWeight × timezone
+
eloWeight × Elo
```

There should be no arbitrary weighting parameter between these objectives.

After next-tier assignments are complete, rebalance independently inside every tier.

Example:

```text
Tier 1 clubs → rebalance among 1.x groups
Tier 2 clubs → rebalance among 2.x groups
Tier 3 clubs → rebalance among 3.x groups
...
```

Never move a club between tiers during this phase.

Its:

```text

```

is already final.

Only its:

```text

```

may change.

## 29. Human groups should be populated evenly

Before optimizing timezone, determine how many active groups are required.

Let:

```text
H = number of human clubs assigned to the tier
C = CLUBS_PER_DIVISION
M = maximum groups allowed for this tier
```

If:

```text
H == 0:
    activeGroups = 0
```

Otherwise:

```text
activeGroups =
    min(M, ceil(H / C))
```

If:

```text
H > M × C
```

throw/log a structural capacity error.

Do not silently discard clubs.

---

## 30. Human capacity distribution

Humans should be distributed as evenly as mathematically possible between those groups.

Let:

```text
G = activeGroups

baseSize = floor(H / G)
extra = H mod G
```

Target human capacities:

```text
groups 1..extra:
    baseSize + 1

remaining groups:
    baseSize
```

Example:

```text
20 humans
3 groups

baseSize = 6
extra = 2
```

Human group sizes:

```text
7
7
6
```

not:

```text
8
8
4
```

Then AI may fill empty competition seats afterward if required.

This change itself improves competitive fairness.

## 31. Timezone representation

Each human club must have an IANA timezone inherited from its owner/profile, for example:

```text
America/Moncton
America/Sao_Paulo
Europe/London
Asia/Tokyo
```

For grouping, convert each timezone to its UTC offset in minutes at:

```text
nextSeason.startAt
```

Use the timestamp at 12:00 UTC on that date so there is no ambiguity around midnight/DST transition boundaries.

Example:

```text
America/Moncton → -180
Europe/London   → +60
```

Do not permanently store only the offset.

Store the IANA timezone; calculate the offset for each season because daylight-saving rules can change it.

If no timezone exists:

```text
timezone = UTC
offset = 0
```

and log the missing profile timezone.

---

## 32. Circular timezone distance

Timezone is circular.

`UTC+12` and `UTC-12` are effectively adjacent rather than 24 hours apart.

Let:

```text
rawDistance =
    abs(offsetA - offsetB)
```

Then:

```text
timezoneDistance =
    min(
        rawDistance,
        1440 - rawDistance
    )
```

All values are in minutes.

Examples:

```text
UTC-3 vs UTC-4
distance = 60

UTC+11 vs UTC-11
raw = 1320
circular = 120
```

---

## 33. Timezone group cost

For each proposed group `g`, calculate every human-human pair.

For clubs `i` and `j`:

```text
d(i,j) = circular timezone distance in minutes
```

Group timezone cost:

```text
TZCost(g) =
    Σ [d(i,j)²]
```

for every unique pair.

Total assignment cost:

```text
TotalTZCost =
    Σ TZCost(g)
```

Squaring the distance deliberately penalizes large timezone separations more heavily.

For example:

```text
2-hour gap:
120² = 14,400

4-hour gap:
240² = 57,600
```

So one badly misplaced club is worse than several tiny differences.

---

## 34. Initial social-first assignment

Build groups independently for each finalized target division. First find an
assignment with the best feasible social objective from section 27.1 while
respecting the balanced human capacities. Only assignments with equivalent
social quality may proceed to timezone comparison.

Within that socially optimal set, use the following timezone procedure. Any
candidate that lowers the social objective is rejected before timezone cost is
considered.

### 34.1 Sort

Convert every offset into:

```text
normalizedOffset =
    ((offsetMinutes % 1440) + 1440) % 1440
```

Sort by:

```text
normalizedOffset ASC
random tie-breaker
```

### 34.2 Try every possible circular starting position

For `N` humans, evaluate:

```text
rotation 0
rotation 1
...
rotation N-1
```

For each rotation:

1. Rotate the sorted list.
2. Divide it sequentially according to the predetermined target group capacities.
3. Calculate `TotalTZCost`.

Choose the rotation with the smallest `TotalTZCost`.

Tie after social and timezone objectives:

```text
random tie-breaker
```

This correctly handles clusters spanning the UTC date line.

With the expected number of clubs, evaluating every rotation is trivial computationally.

---

## 35. Secondary Elo objective

After the initial timezone-optimal assignment, calculate:

```text
globalTierMeanElo =
    sum(all Elo) / H
```

For each group:

```text
groupMeanElo =
    sum(group Elo) / groupHumanCount
```

Elo imbalance:

```text
EloCost =
    Σ groupHumanCount
      × (groupMeanElo - globalTierMeanElo)²
```

Weighting by group size prevents tiny groups from having disproportionate influence.

Lower is better.

Perfect balance:

```text
EloCost = 0
```

---

## 36. Elo balancing must not materially damage timezone grouping

After the initial social/timezone solution, perform pair swaps between groups.

For every pair of human clubs in different groups:

```text
swap A ↔ B
```

Calculate:

```text
newSocialCost
newTZCost
newEloCost
```

A swap is eligible only if:

```text
newSocialCost == currentSocialCost
AND
newTZCost == currentTZCost
```

Then accept the eligible swap that produces the largest reduction in:

```text
EloCost
```

Tie:

```text
random tie-breaker
```

Apply the swap.

Repeat.

Stop when no swap exists satisfying:

```text
newSocialCost == currentSocialCost
AND
newTZCost == currentTZCost
AND
newEloCost < currentEloCost
```

Use an epsilon for floating-point Elo comparison:

```text
ELO_COST_EPSILON = 0.000001
```

Timezone cost itself uses integers and therefore needs no epsilon.

This produces a true lexicographic optimization:

```text
social grouping never gets worse
timezone never gets worse
Elo improves where possible
```

---

## 37. Why not allow a 5% timezone degradation for better Elo?

Do not do that initially.

A weighted/tolerance model creates an arbitrary policy question:

> "How many hours of timezone inconvenience is 100 Elo worth?"

There is no defensible universal answer.

The strict hierarchy:

```text
social grouping first
timezone second
Elo third
```

is simpler and aligns exactly with the stated product requirement.

If later telemetry shows groups remain severely imbalanced, the policy can be revisited.

Humans are grouped first.

Then use the existing AI filler mechanism to fill remaining competition slots.

```text

7
6
```

Then AI:

```text

Group B: 7 humans + 1 AI

```

Do not include AI Elo in the balancing calculation.

AI does not need a meaningful timezone.

## 39. Promotion and group-assignment interaction

Never use friendship, friends-of-friends, or timezone to determine who gets
promoted.

These are grouping criteria, not sporting criteria.

The sequence must remain:

```text
sporting result
→ Elo cross-group comparison
→ target tier
→ same-division social group allocation
→ timezone/Elo group allocation
```

---

## 40. Promotion and Elo-group-balancing interaction

Do not use a club's previous group Elo distribution when deciding its new group.

Every rollover starts from the complete set of clubs assigned to the tier.

For example:

```text
2.1 club
2.2 club
promoted 3.1 club
promoted 3.3 club
relegated 1.x club
```

all enter the same Tier-2 rebalancing pool.

Their previous group labels have no priority.

---

## 41. Group IDs after randomized assignment

After finding the optimized groups, assign them to group identifiers
deterministically. The random tie-breaker chooses membership only when all
higher-priority objectives are tied; it must not make group IDs ambiguous.

Sort resulting groups by:

```text
1. circular median timezone offset ASC
2. mean Elo DESC
3. lowest clubId ASC
```

Then assign:

```text
Tier 3 group 1
Tier 3 group 2
Tier 3 group 3
...
```

This gives stable identifiers for the groups produced by a particular
assignment.

For determining the group's timezone representative, use the club whose normalized offset minimizes the sum of circular distances to every other club in that group.

Tie:

```text
lowest normalized offset
then clubId
```

`computeNextTierAssignments` should conceptually become two phases.

### Phase A — determine tiers

For each human club:

```text

STAY
RELEGATE
EXIT/INACTIVE
```

Resolve:

```text

promotion vacancies
promotion candidate rounds

Output:

```

Examples of reason:

```text

PROMOTION_ELO_RUNNER_UP
PROMOTION_ELO_THIRD
STAY
RELEGATION
```

Do not assign specific group IDs here.

### Phase B — build groups

For every target tier:

```text

maximize direct-friend grouping
maximize friends-of-friends grouping
timezone optimization
Elo balancing
random tie-breaker
assign group IDs
insert AI fillers
```

Then create/sync next-season memberships.

## 44. Fix `promotionStatus`

The current:

```text

```

hardcoding in `syncClubSeasons` should be removed.

Use the same candidate computation that powers rollover.

During an active season:

```text

```

This represents the currently automatic promotion position.

### Eligible human rank 2 or lower

```text

```

because additional upper-tier vacancies can promote remaining candidates, with

```text

```

General rule:

```text
PROMOTED =
    candidates that would definitely be selected
    if current final table froze now

POSSIBLE =
    candidates in the first partially selected promotion pool after Round 1

NONE =
    everyone else
```

After final rollover:

```text
actual promoted clubs → PROMOTED
all others → NONE
```

Do not maintain separate UI-only promotion logic.

Call the same domain calculation used by the rollover.

- exclude it from promotion candidate pools;

## 57. Concurrency

Two matches involving the same club must not corrupt Elo.

Elo finalization needs transaction-level serialization.

When processing Match X:

```text

read current Elo
calculate
write both
commit
```

Always lock clubs in deterministic `clubId ASC` order to avoid deadlocks.

Then process another match.

Do not calculate Elo from stale parallel snapshots.

## 66. Final behavioral summary

The resulting system becomes:

```text
NORMAL LEAGUE TABLE
    ↓
AI can influence results
but AI cannot be promoted
    ↓
Rank humans inside each group
    ↓
Take all human #1s when capacity permits
    ↓
Need more promotions?
Pool all remaining human #2s, #3s, and lower by Elo
    ↓
Determine each club's new tier
    ↓
Forget old group membership
    ↓
Spread humans evenly among required groups
    ↓
Group friends and friends of friends within each division
    ↓
Cluster by timezone
    ↓
Among equally good social/timezone arrangements,
balance mean Elo
    ↓
Insert AI filler
    ↓
Start next season
```

The key design decision is that **social grouping comes first, timezone comes
second, and Elo comes third**. Elo should balance groups, but it should never
compete numerically with either social cohesion or timezone. This also pairs
well with using Elo for promotion selection, because it reduces the chance
that one group becomes consistently much harder than another.
