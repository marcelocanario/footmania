# Match Simulator Overhaul Plan — Possession-State Engine with Explicit Influence Math

**Status:** Proposal only. This document does not change the simulator.

**Goal:** Replace the current match calculations with a live, state-dependent football simulation in which possession, territory, pressure, chances, xG, shots, goals, cards, substitutions and tactical effects emerge naturally from a continuous football state.

The simulator should feel like a real match rather than a sequence of unrelated minute rolls. Team quality and tactics must shape how possessions develop; randomness must create believable variation without making the match feel arbitrary.

The intended long-run influence is approximately:

```text
team / player state    ≈ 40%
tactics                ≈ 35%
luck / stochasticity   ≈ 25%
```

These are **not hard-coded outcome percentages**. The first-pass formulas below are constructed so that, after signal normalization, the latent action-choice model begins close to that relationship mathematically.

---

# 0. Core modelling rule

The fundamental unit of simulation is the **possession sequence**, not the minute.

The UI may still display the match minute-by-minute, but internally the engine runs football actions with stochastic durations.

```text
MATCH STATE
    ↓
team in possession
    ↓
phase + zone + lane
    ↓
available football actions
    ↓
real-football baseline probabilities
    ↓
team-quality adjustment
    ↓
tactical adjustment
    ↓
live context adjustment
    ↓
probabilistic action choice
    ↓
action duration
    ↓
new state
    ↓
repeat
```

There must be:

```text
no predetermined winner
no predetermined score
no future event list
no hidden comeback bonus
no arbitrary momentum bonus
no direct possession target
no formation rock-paper-scissors table
```

Possession, field tilt, pressure, shots and xG are outputs of the simulated football.

# 3. Why the default team/tactics/luck scales are 2.30 / 2.15 / 1.00

For every meaningful action choice, compare the candidate actions using latent utilities.

Let the standardized football signals be:

```text
Z_team    ~ approximately mean 0, variance 1
Z_tactics ~ approximately mean 0, variance 1
```

For a pairwise comparison between two actions, multinomial-logit / softmax sampling is equivalent to adding Gumbel noise to each action utility. The difference between two independent standard Gumbel draws has a logistic distribution with variance:

```text
Var(luck) = π² / 3 ≈ 3.2899
```

To start near the desired latent variance proportions:

```text
Team      : Tactics : Luck
0.40      : 0.35    : 0.25
```

choose deterministic scales so that:

```text
teamScale²     / Var(luck) = 0.40 / 0.25
tacticsScale²  / Var(luck) = 0.35 / 0.25
```

Therefore:

```text
teamScale
= sqrt((0.40 / 0.25) * π²/3)
≈ 2.294

 tacticsScale
= sqrt((0.35 / 0.25) * π²/3)
≈ 2.146
```

Rounded defaults:

```text
teamLogitScale    = 2.30
tacticsLogitScale = 2.15
randomnessScale   = 1.00
```

This does **not** mean each match is literally 40/35/25. It means the default latent action-choice model begins with that approximate variance structure when its team and tactical signals are standardized.

Downstream goal conversion, cards, injuries and other low-frequency events add further stochastic variance, while many possession actions average some randomness out. The final match-level split must still be measured with the harness, but the implementation begins from a mathematically justified point rather than arbitrary weights.

# 4. Core action probability formula

For every possible action `a` from current state `s`, the empirical football model provides:

```text
P0(a | s)
```

This is the baseline probability for ordinary real-football conditions.

The game modifies the baseline in log-odds space:

```text
modifier(a) =
    teamLogitScale    * Z_team(a)
  + tacticsLogitScale * Z_tactics(a)
  + contextLogit(a)
```

Randomness controls how strongly deterministic differences pull the game away from the baseline:

```text
adjustedModifier(a) = modifier(a) / randomnessScale
```

Then:

```text
rawWeight(a) =
    P0(a | s)
    * exp(adjustedModifier(a))
```

and:

```text
P(a | s) =
    rawWeight(a)
    / sum(rawWeight(k) for all legal actions k)
```

This is equivalent to a baseline-relative softmax.

Important properties:

```text
If all modifiers are zero:
    P(a|s) = P0(a|s)

Higher teamLogitScale:
    player/team differences matter more

Higher tacticsLogitScale:
    tactical choices matter more

Higher randomnessScale:
    team/tactical differences are softened and outcomes become less predictable
```

`randomnessScale` does not change the real-football baseline when the competing teams and tactics are neutral.

---

# 5. No separate random bonus

Do not implement:

```text
luckBonus = random(-X, +X)
```

for every action.

The categorical action draw itself is the event-level luck.

A state may produce:

```text
P(progress) = 0.48
P(retain)   = 0.31
P(turnover) = 0.16
P(foul)     = 0.05
```

The random draw decides which one actually occurs.

That is enough to generate natural variation.

For the first version, do **not** add a separate match-wide "good day / bad day" random modifier. It would make luck harder to control and can be introduced later only if the simulation proves too stable.

# 6. Robust normalization of player attributes

The 2.30 and 2.15 scales only have the intended meaning if team and tactical signals are on comparable scales.

Normalize every match-relevant player attribute against the current active football population using robust statistics.

For attribute `x`:

```text
median_x = median(x across active senior players)
MAD_x    = median(abs(x - median_x))

robustSigma_x = max(1.4826 * MAD_x, minimumSafeSigma)

Z_attr(x) =
    clamp(
        (x - median_x) / robustSigma_x,
        -3,
        +3
    )
```

`1.4826 * MAD` is a robust estimate of standard deviation for approximately normal data.

This should be recalculated when the game world materially changes, such as at season setup, not every match tick.

This avoids hard-coding statements such as:

```text
80 passing = elite
60 passing = average
```

The game population determines what "one standard deviation better" means.

# 7. Position suitability

Keep the existing Elifoot-derived compatibility matrix from the previous plan.

For player `p` assigned to role `r`:

```text
fit(p,r) = positionCompatibility[naturalPosition(p)][r]
```

Position suitability affects the player's usable match attributes before they enter action-quality calculations.

For match-relevant attribute `x`:

```text
usableAttribute(p,x,r) =
    x(p)
    * fit(p,r)
    * readiness(p)
```

Do not later add another generic out-of-position penalty.

One football cause must have one defined path through the engine.

# 8. Energy and readiness

Keep the current bounded readiness curve:

```text
readiness(p) =
    1 - 0.28 * (max(0, 75 - energy(p)) / 75)^1.35
```

Properties:

```text
energy >= 75 → readiness = 1.00
energy = 0   → readiness = 0.72
```

Energy therefore matters without making exhausted stars completely useless.

Do not add a second generic `fatigueSignal` later. Fatigue changes the player's usable attributes and action execution directly.

# 9. Stamina capacity and recovery

Keep the existing derived stamina concept:

```text
physicalSkill = mean(speed, strength/physical)

agePenalty =
    1.8 * max(0, age - 27)

physicalBonus =
    0.25 * (physicalSkill - 50)

staminaCapacity =
    clamp(
        100 - agePenalty + physicalBonus,
        45,
        100
    )
```

Rest quality:

```text
restQuality =
    clamp(
        100
        - 1.10 * minutesPlayedLast24h
        - 0.35 * minutesPlayedLast72h
        + 15 * daysSinceLastMatch,
        0,
        100
    )
```

Daily recovery:

```text
dailyRecovery =
    clamp(
        4
        + 0.04 * staminaCapacity
        + 0.02 * restQuality,
        4,
        10
    )

energyNextDay =
    min(100, energy + dailyRecovery)
```

Rest affects the match through energy rather than an additional hidden rest modifier.

# 10. Fatigue should use actual simulated time

Because the new engine advances by actions measured in seconds, fatigue should no longer be a coarse seven-minute tick.

For active player `p` over an action lasting `dtSeconds`:

```text
roleLoad = {
    GK:  0.20,
    DEF: 0.75,
    MID: 1.00,
    ATT: 0.90
}
```

```text
pressLoad =
    1 + 0.22 * pressing/100
```

```text
styleLoad = {
    cautious:  0.92,
    balanced:  1.00,
    attacking: 1.10
}
```

```text
ageLoad =
    1 + 0.006 * max(0, age - 27)
```

Then:

```text
fatiguePerMinute(p) =
    0.32
    * roleLoad(p)
    * pressLoad
    * styleLoad
    * ageLoad
    * (100 / staminaCapacity(p))
    * (1 + 0.35 * (1 - energy(p)/100))
```

And:

```text
energyLoss =
    fatigueScale
    * fatiguePerMinute(p)
    * dtSeconds/60
    * involvementLoad(p, currentAction)
```

where `involvementLoad` is derived from whether the player's zone/role was actively involved in the action.

It should average approximately 1.0 over a normal match for a typical starter.

This makes high-intensity football consume energy through the actual event stream rather than through an unrelated clock penalty.

# 17. Action-quality aggregation

For the relevant attacking players, calculate their standardized usable attributes.

If an action uses `n` relevant attribute components:

```text
actorQuality =
    sum(Z_usableAttribute_i)
    / sqrt(n)
```

The `sqrt(n)` denominator keeps the scale approximately stable as more independent attributes are included.

If several players contribute to the action:

```text
attackQuality =
    weightedMean(actorQuality, zoneInvolvementWeight)
```

The defender/resistance side is calculated the same way:

```text
defenceQuality =
    weightedMean(defenderQuality, zoneInvolvementWeight)
```

Then form the standardized contest signal:

```text
Z_team_raw =
    (attackQuality - defenceQuality) / sqrt(2)
```

Finally:

```text
Z_team = clamp(Z_team_raw, -2.5, +2.5)
```

If attack and defence quality are approximately unit-normalized, division by `sqrt(2)` keeps their difference approximately unit variance.

This is the signal multiplied by `teamLogitScale = 2.30`.

# 18. Player roles create different football

Do not make overall rating the only meaningful number.

Different actions naturally emphasize different attributes.

Examples:

```text
excellent passer
→ better retention and progression

fast winger
→ better wide progression and counters

strong centre-back
→ better central defensive duels

good finisher
→ better shot conversion

good goalkeeper
→ lower opponent conversion
```

This allows equally rated squads to play differently because their skill distributions differ.

# 19. Formation is geometry, not a bonus

Formation should determine:

```text
zone support
passing outlets
central density
wide support
players committed forward
defensive coverage
counter vulnerability
```

Each formation slot contributes a smooth support kernel to nearby zones.

For a formation slot with nominal zone `z0`, define support for zone `z` as:

```text
support(slot,z) =
    exp(-distance(z,z0)^2 / 2)
```

where pitch-state distance is measured on the 3 × 3 grid.

The team's zone support is:

```text
zoneSupport(z) =
    sum(support(slot,z) * playerAvailability(slot))
```

This creates smooth formation influence without a hand-written matchup table.

A player helps most in their own zone, somewhat in adjacent zones, and little in remote zones.

---

# 20. Formation support as a tactical signal

For an action attacking zone `z`, compare attacking formation support against defending coverage:

```text
shapeRaw =
    ln(
        (attackingSupport(z) + ε)
        /
        (defendingCoverage(z) + ε)
    )
```

Normalize `shapeRaw` over representative legal formations to produce:

```text
Z_shape
```

with approximately unit variance and clamp to:

```text
[-2.5, +2.5]
```

This is a tactical component.

Formation strength therefore emerges from spatial support and exposure rather than:

```text
4-3-3 beats 4-4-2
```

# 21. Direction is route preference

Represent lateral lane coordinates as:

```text
LEFT   = -1
CENTRE =  0
RIGHT  = +1
```

For manager direction:

```text
LEFT:
    preferredCoordinate = -1

MIDDLE:
    preferredCoordinate = 0

RIGHT:
    preferredCoordinate = +1
```

For an action entering lane `L`:

```text
directionRaw =
    -abs(L - preferredCoordinate)
```

For `WIDE`:

```text
directionRaw = abs(L)
```

For `BALANCED`:

```text
directionRaw = 0
```

Center the available-action direction values within the current state:

```text
centeredDirection(a) =
    directionRaw(a)
    - mean(directionRaw(k) for legal actions k)
```

Then robustly standardize across representative states to produce:

```text
Z_direction
```

Direction therefore redistributes attack routes without directly increasing player ability.

# 22. Style as action preference

Each action definition contains semantic features rather than a manually tuned tactic table.

Recommended features:

```text
directness ∈ [-1,+1]
retention  ∈ [-1,+1]
risk       ∈ [0,1]
transitionAffinity ∈ [0,1]
```

Examples conceptually:

```text
RECYCLE_BACKWARD
retention high
directness low
risk low

DIRECT_BALL
directness high
retention low
risk high

COUNTER PROGRESS
directness high
transitionAffinity high
```

Map style to a preference vector.

### CONTROL

```text
styleRaw =
    + retention
    - directness
    - risk
```

### COUNTER

During `COUNTER` phase:

```text
styleRaw =
    + directness
    + transitionAffinity
    + risk * 0.5
```

Outside `COUNTER` phase:

```text
styleRaw =
    0.25 * directness
```

### PRESS

In possession:

```text
styleRaw = 0
```

Out of possession / recovery actions:

```text
styleRaw = pressureOpportunity
```

Center and robustly normalize these values to produce:

```text
Z_style
```

These semantic formulas are engine definitions, not user tunables.

# 23. Pressing

Pressing already exists as a numeric tactical input.

Normalize:

```text
pressIntensity = pressing / 100
```

Pressing affects opponent action possibilities rather than adding generic team strength.

During an opponent build-up or progression action:

```text
pressRaw =
    pressIntensity
    * localPressSupport
    * pressingExecution
    * (1 - localDefensiveOrganisationPenalty)
```

This increases the relative utility of outcomes such as:

```text
TURNOVER
DIRECT_ESCAPE
BACKWARD_RECYCLE
FOUL_DRAWN
```

and reduces clean progression.

If the press is beaten, the same press intensity increases space behind it through the defensive-organisation model.

Pressing costs energy through the fatigue equation and raises duel/foul exposure.

There is no separate generic `pressingSignal` after these effects.

# 24. Tactical familiarity

Keep familiarity separately for:

```text
formation
style
pressing
direction
```

Growth after use:

```text
growthRate =
    1 - exp(-3 / scheduledSeasonGames)

newFamiliarity =
    familiarity
    + (100 - familiarity) * growthRate
```

Decay while unused:

```text
newFamiliarity =
    familiarity * exp(-0.005 * daysWithoutUse)
```

When switching, retrieve familiarity with the target component rather than deriving it only from the current tactic.

Similar systems may transfer partial familiarity:

```text
transfer =
    max(0, oldFamiliarity - targetFamiliarity)
    * similarity
    * 0.35
```

```text
effectiveFamiliarity =
    clamp(targetFamiliarity + transfer, 0, 100)
```

# 25. Tactical execution

For component familiarity `F`:

```text
execution(F) =
    0.60 + 0.40 * F/100
```

A new tactic therefore still functions, but less efficiently.

Apply familiarity to the tactical component it belongs to:

```text
executedStyle     = Z_style     * execution(styleFamiliarity)
executedShape     = Z_shape     * execution(formationFamiliarity)
executedDirection = Z_direction * execution(directionFamiliarity)
executedPress     = Z_press     * execution(pressingFamiliarity)
```

Do not add familiarity as another team-strength bonus.

---

# 26. Combine tactical components without extra tuning weights

For an action, collect only the tactical components that are relevant in that state.

Example:

```text
components = [
    executedStyle,
    executedShape,
    executedDirection,
    executedPress
]
```

Ignore inactive / non-applicable components.

If `n` components are active:

```text
Z_tactics_raw =
    sum(activeComponents) / sqrt(n)
```

Then normalize this combined signal using a robust scale derived by enumerating representative legal tactic/formation combinations:

```text
Z_tactics =
    clamp(
        Z_tactics_raw / robustTacticalSigma,
        -2.5,
        +2.5
    )
```

`robustTacticalSigma` is generated by the model calibration tooling, not exposed as a normal game setting.

This gives tactics an approximately unit-variance signal suitable for `tacticsLogitScale = 2.15` without a long list of hand-tuned style-vs-formation-vs-direction weights.

# 27. Why tactics can contribute ~35% without overpowering players

Tactics modify **which football actions are attempted and which areas are exploited**.

They do not directly raise player attributes.

For example:

```text
Counter tactic
→ more direct transition choices
→ more attacks against temporarily disorganised defence
```

but whether those actions succeed still depends on:

```text
speed
passing
dribbling
position fit
energy
opponent defensive quality
```

Therefore good tactics can make a weaker squad outperform expectations without making weak players execute like elite players.

# 28. Action duration: semi-Markov timing

Every successful or failed action consumes match time.

Use empirical Gamma distributions by action/phase:

```text
dt ~ Gamma(shape[action,phase], scale[action,phase])
```

Then:

```text
dt *= tempoScale
```

The baseline Gamma parameters are fitted offline from real match-event timing.

Different styles already affect tempo indirectly because they select different action types:

```text
CONTROL
→ more retain/recycle actions
→ longer possessions

COUNTER
→ more direct progress actions
→ shorter possessions
```

Therefore do not add another large style-tempo multiplier unless empirical validation proves necessary.

# 29. Possession is an output

Track controlled-ball time directly:

```text
homePossessionSeconds
awayPossessionSeconds
```

Then:

```text
homePossession =
    homePossessionSeconds
    /
    (homePossessionSeconds + awayPossessionSeconds)
```

Do not roll a separate possession percentage.

A control team should obtain more possession because it retains the ball more successfully and for longer periods.

A counterattacking team may naturally have low possession but high-quality transition chances.

# 30. Turnovers preserve location

When possession changes, preserve the physical zone.

Example:

```text
Team A loses possession in ATT-R
```

Team B begins possession around:

```text
DEF-L
```

A turnover in:

```text
DEF-C
```

is immediately far more dangerous.

This makes turnovers, pressing and player mistakes meaningful without special event scripting.

# 31. Defensive organisation

Track a derived variable:

```text
defensiveOrganisation ∈ [0,1]
```

Normal baseline organisation comes from formation support and active personnel.

A turnover creates disruption:

```text
disruption =
    f(
        turnoverZone,
        playersCommittedForward,
        pressingIntensity,
        redCards,
        fatigue
    )
```

Then recover exponentially:

```text
organisation(t) =
    baselineOrganisation
    - disruption * exp(-t / recoveryTime)
```

`recoveryTime` should be derived primarily from local player positioning, speed, stamina and formation support rather than exposed as another global tunable.

This single state produces natural transition vulnerability.

---

# 32. Counterattack phase

After a turnover, calculate a counter opportunity:

```text
counterOpportunity =
    advancedRecoveryValue
    * opponentPlayersCommittedForward
    * (1 - opponentDefensiveOrganisation)
    * ownCounterPreference
```

Normalize the components to `[0,1]`.

Instead of a hard threshold, convert it smoothly:

```text
P(counterPhase) =
    logistic(
        4 * (counterOpportunity - 0.5)
    )
```

If selected:

```text
phase = COUNTER
```

Counter advantage decays naturally as the defence recovers:

```text
counterAdvantage(t) =
    initialCounterAdvantage
    * exp(-t / recoveryTime)
```

The phase ends when the defence reorganises or the attack slows into normal progression/sustained attack.

# 33. Sustained pressure without a momentum stat

Do not create:

```text
momentum = +20
```

Sustained pressure emerges when an attacking team repeatedly recovers clearances and second balls in advanced zones.

Example:

```text
ATT-C
→ blocked shot
→ clearance to MID-C
→ attacking team wins second ball
→ ATT-R
→ cross
→ clearance
→ attacking team wins second ball
→ ATT-C
→ shot
```

This naturally creates:

```text
high attacking-third possession
high field tilt
repeated commentary events
rising chance volume
```

without a hidden positive-feedback bonus.

# 34. Expected possession value / expected threat

Calculate an internal value for each possession state.

Let:

```text
V(s) = expected scoring value before the current possession terminates
```

Solve from the transition model:

```text
V(s) =
    P(shot | s) * E[xG | shot,s]
    +
    sum(
        P(s' | s) * V(s')
        for non-terminal next states s'
    )
```

This can be solved by value iteration from the baseline transition matrix and updated approximately for live tactical/player modifiers.

Use `V(s)` for:

```text
commentary importance
AI tactical evaluation
dangerous-attack detection
field-pressure analysis
substitution impact estimates
```

Do not add it back into event probabilities as another bonus.

---

# 35. Shots are possession transitions

A shot is one possible action from sufficiently advanced states.

Example:

```text
ATT-C / SUSTAINED_ATTACK

possible:
retain
progress
switch
cross
shot
turnover
```

The baseline football model determines ordinary shot propensity.

Team/player and tactical signals modify the relative probability through the same action formula.

There is no separate per-minute shot roll.

---

# 36. Shooter selection

When `SHOT` occurs, select only plausible actors from the current possession state.

For candidate player `p`:

```text
shooterWeight(p) =
    zoneInvolvement(p)
    * roleShotPresence(p)
    * max(0.1, finishingAvailability(p))
```

Normalize to a categorical distribution and draw the shooter.

The exact positional involvement factors should be derived from formation/zone geometry rather than a long manually tuned scorer table.

---

# 37. Shot-quality model

Use a real-football baseline xG for the shot situation:

```text
p0_xG =
    baselineXG(
        shotZone,
        shotType,
        previousAction,
        defensiveOrganisation,
        setPieceState
    )
```

Then adjust for shooter versus goalkeeper quality in log-odds space:

```text
Z_finishGK =
    (Z_finishing(shooter) - Z_goalkeeping(goalkeeper)) / sqrt(2)
```

First-pass conversion model:

```text
logit(xG) =
    logit(p0_xG)
    + 0.55 * Z_finishGK
    + homeShotQualityShift
```

Then:

```text
xG = sigmoid(logit(xG))
```

Clamp only for numerical safety:

```text
0.01 ≤ xG ≤ 0.75
```

The `0.55` coefficient is a first-pass model parameter representing an odds multiplier of about:

```text
exp(0.55) ≈ 1.73
```

for a one-standard-deviation shooter-vs-goalkeeper advantage.

Treat this as part of the football-baseline model and fit it later from simulation / empirical calibration rather than making it another normal product setting.

Critical rule:

```text
P(goal | shot) = xG
```

Then:

```text
goal = RNG() < xG
```

---

# 38. Avoid tactical double-counting in xG

Tactics should usually affect shot quality **by changing how the chance was created**:

```text
counterattack
→ lower defensive organisation
→ better baseline shot context
→ higher xG
```

```text
wide overload
→ different shot/cross location
→ different baseline shot context
```

Do not then add another generic `tacticsBonus` directly to xG.

This preserves the rule:

```text
one cause → one engine path
```

---

# 39. Goalkeeper influence

Goalkeeper quality primarily affects:

```text
shot conversion
```

Secondary goalkeeper actions may include:

```text
cross claiming
rebound control
distribution after saves
```

A goalkeeper should not substantially prevent shots from existing; defence and possession state should handle chance prevention.

# 40. Home advantage formula

Keep only one configurable target:

```text
homeXgAdvantageTarget = 0.25
```

Let the empirical neutral-team baseline be:

```text
neutralXG
```

For example, if the baseline model produces approximately:

```text
neutralXG = 1.30 per team
```

then the desired home ratio is:

```text
homeRatio =
    (neutralXG + homeXgAdvantageTarget)
    / neutralXG
```

For 1.30 and +0.25:

```text
homeRatio ≈ 1.1923
```

Split the home advantage 70/30 between chance creation and shot quality **multiplicatively**:

```text
homeCreationMultiplier =
    homeRatio^0.70

homeShotQualityMultiplier =
    homeRatio^0.30
```

For the example:

```text
homeCreationMultiplier ≈ 1.131
homeShotQualityMultiplier ≈ 1.054
```

Use:

```text
homeCreationLogShift = ln(homeCreationMultiplier)
homeShotQualityShift = ln(homeShotQualityMultiplier)
```

The first is applied to attacking action creation/progression weights; the second is added to shot log-odds.

Neutral venue:

```text
both shifts = 0
```

No additional home player-skill multiplier should exist.

# 41. Morale and recent form

Keep morale/form bounded and place it inside the team/state path only once.

```text
squadMorale =
    0.75 * mean(starterMorale)
    + 0.25 * mean(availableSquadMorale)
```

```text
formScore =
    clamp(
        50
        + 3.33 * (actualPointsLast5 - expectedPointsLast5),
        0,
        100
    )
```

```text
moraleForm =
    0.80 * squadMorale
    + 0.20 * formScore
```

Instead of multiplying the whole team force, convert it into a small standardized execution offset:

```text
Z_morale =
    (moraleForm - 50) / 50
```

and let it slightly modify the usable player/action-quality signal:

```text
Z_team_effective =
    clamp(
        Z_team + 0.15 * Z_morale,
        -2.5,
        +2.5
    )
```

This keeps morale meaningful but clearly subordinate to player quality.

The `0.15` is a model coefficient and should live with the baseline model constants rather than become a normal game-config knob.

# 42. Club level / reputation

Reputation has been removed and must not be reintroduced.

Club `level` / `tier` is not a match-strength input.

It may affect non-match systems such as:

```text
attendance
revenue
transfers
AI prestige behaviour
commentary context
```

but the match engine must not read club level as hidden football strength.

# 43. Fouls and cards should happen inside football actions

Fouls should normally arise from actual contested actions rather than unrelated global rolls.

Example:

```text
MID-C progression
→ defensive challenge
→ tackle succeeds
OR attacker progresses
OR foul
OR foul + card
```

Use a centred hazard / categorical model based on:

```text
player discipline
pressing intensity
fatigue
defensive exposure
duel difficulty
current yellow-card state
```

The average neutral-match card rate should remain close to the empirical baseline stored in the football model.

Do not add only-positive multipliers to a nominal baseline or the average will drift upward.

---

# 44. Red cards

Second-yellow and straight-red probabilities should be separate.

When a dismissal occurs:

1. Remove the player from zone/role contributions.
2. Remove their action availability.
3. Recalculate formation support.
4. Reduce local defensive organisation where appropriate.
5. Allow the manager/AI to reorganise.

Do not apply:

```text
(playersOnPitch / 11)^2
```

as an additional blanket penalty.

The loss of a striker, midfielder and centre-back should produce different consequences because the possession/formation model uses different zones and actions.

---

# 45. Injuries

Injury probability should depend on:

```text
fatigue
age
recent workload
physical duel involvement
player durability if available
stochastic draw
```

An injury is a live state change and should immediately affect future actions.

Age should not directly reduce technical quality inside the match; it should matter mainly through physical capacity and recovery.

---

# 46. Penalties

Penalties should emerge mainly from actions in dangerous zones.

Inputs include:

```text
box entry / ATT-C presence
defensive pressure
duel difficulty
tackle behaviour
discipline
random event draw
```

Penalty conversion is a separate shooter-vs-goalkeeper event.

---

# 47. Set pieces

Treat set pieces as special possession-start states:

```text
CORNER_LEFT
CORNER_RIGHT
FREE_KICK_WIDE
FREE_KICK_CENTRAL
THROW_IN
GOAL_KICK
PENALTY
```

Each uses baseline transition distributions.

Example:

```text
CORNER
→ cross
→ header / clearance
→ second ball / possession end
```

Set-piece events therefore flow naturally into normal possession rather than existing as isolated commentary rolls.

---

# 48. Score state affects behaviour, not hidden finishing luck

Do not implement:

```text
losing team gets goal bonus
winning team gets finishing penalty
```

For AI teams, score and time affect tactical decisions.

Example late and losing:

```text
pressing ↑
players committed forward ↑
directness ↑
risk tolerance ↑
recycling ↓
```

Example late and winning:

```text
risk tolerance ↓
defensive support ↑
recycling ↑
counter preference ↑
```

Human-controlled teams use the manager's choices instead.

# 49. Substitutions

A substitution immediately changes:

```text
usable player attributes
zone support
energy distribution
pressing ability
finishing options
counter speed
formation coverage
```

The next simulated action uses the new state.

Nothing in the match may have been precomputed beyond the current state.

# 50. AI substitutions

Keep a normalized need score:

```text
substitutionNeed =
    0.45 * fatigueNeed
    + 0.25 * zoneDeficit
    + 0.15 * scoreUrgency
    + 0.15 * cardOrInjuryRisk
```

All components are normalized to `[0,100]`.

Replacement value:

```text
replacementValue =
    0.65 * effectiveSkill
    + 0.25 * energy
    + 0.10 * (fit * 100)
```

The AI should additionally prefer replacements that improve the currently weak zones/actions rather than only maximizing generic overall value.

Add small seeded timing uncertainty so substitutions are not mechanically identical every match.

# 51. AI tactical decisions

The AI should evaluate tactics from the same state model available to the human player.

For each reasonable candidate tactical change, estimate short-horizon effects on:

```text
expected possession value
field tilt
chance-generation rate
counter vulnerability
fatigue cost
score requirement
```

Use the existing `V(state)` / expected-threat model for this estimate.

No privileged AI result bonus is allowed.

```text
teamPossession =
```

# 54. Commentary filtering with expected-threat change

The engine may simulate hundreds of low-level actions.

Do not show all of them.

For state transition:

```text
DeltaV = V(after) - V(before)
```

Large positive `DeltaV` suggests:

```text
important progression
dangerous counter
major chance creation
```

Large negative `DeltaV` suggests:

```text
dangerous turnover
lost attacking opportunity
```

Combine `abs(DeltaV)` with event type to decide commentary importance.

Always show:

```text
goals
shots of meaningful quality
major saves
cards
injuries
penalties
important set pieces
major tactical changes
```

This produces natural event density without artificial commentary timing.

# 56. First-pass influence verification

The formulas already establish the first version:

```text
teamLogitScale    = 2.30
tacticsLogitScale = 2.15
randomnessScale   = 1.00
```

Do **not** instruct the implementation agent to search freely for coefficients until the match "feels 40/35/25".

Instead implement these values first and verify them.

### Controlled influence test

Create representative match states and repeat action choices while varying one source at a time.

For every state record utility variance attributable to:

```text
team term
= teamLogitScale * Z_team

tactical term
= tacticsLogitScale * Z_tactics

stochastic choice
= categorical / implicit Gumbel residual
```

At the normalized action-choice level, expected starting relationship should be close to:

```text
team      ≈ 40%
tactics   ≈ 35%
choice RNG≈ 25%
```

Then run full-match Sobol/Shapley-style experiments:

```text
vary team quality only
vary tactics only
vary RNG seed only
vary combinations
```

Measure effects on:

```text
expected goal difference
xG difference
points expectation
win probability
```

The full-match results may drift somewhat because shot conversion is inherently stochastic and possession randomness partially averages out.

Desired acceptable first range:

```text
Team:     35–45%
Tactics:  30–40%
Luck:     20–30%
```

If adjustment is needed, change only:

```text
teamLogitScale
tacticsLogitScale
randomnessScale
```

Do not introduce new micro-bonuses.

---

# 57. How to tune the three influence scales

If team quality is too weak:

```text
increase teamLogitScale
```

If tactics are too weak:

```text
increase tacticsLogitScale
```

If matches are too deterministic:

```text
increase randomnessScale
```

If matches are too random:

```text
decrease randomnessScale
```

Do not alter the real-football baseline transition probabilities merely to change competitive balance.

The baseline controls what football normally looks like.

The three scales control how strongly the game's teams/tactics move away from that baseline.

Should tend to cause:

```text

transition speed ↓
```

### COUNTER

Should tend to cause:

```text
possession ↓
```

### HIGH PRESS

Should tend to cause:

```text

```

### FRESH SUBSTITUTE

Should improve the actions and zones appropriate to the substitute's skills rather than simply adding a generic strength number.

If a tactical change affects win probability but cannot be seen in possession patterns, territory, event flow or commentary, the simulator has failed the "fun" requirement.

# 68. Final engine flow

```text
MATCH START
    ↓
initial possession
    ↓
PHASE + ZONE + LANE
    ↓
legal actions
    ↓
real-football P0(action | state)
    ↓
calculate action-specific Z_team
    ↓
calculate action-specific Z_tactics
    ↓
P(action)
= P0 * exp((2.30*Z_team + 2.15*Z_tactics + context) / randomnessScale)
    ↓
normalize probabilities
    ↓
seeded categorical draw
    ↓
action occurs
    ↓
sample action duration
    ↓
update clock + energy + state
    ↓
retain possession?
    ├── yes → continue same possession
    └── no  → new possession from turnover/restart state
```

For shots:

```text

    ↓

    ↓
plausible shooter selection
    ↓
baseline shot-context xG
    ↓
shooter vs goalkeeper log-odds adjustment
    ↓
home shot-quality shift if applicable
    ↓
P(goal) = xG
    ↓
seeded Bernoulli draw
    ↓
goal / save / miss / block
    ↓
next football state
```

```text
→ more midfield recycling
```

or:

```text
→ high-value shot
```

None of these requires scripted momentum, hidden comeback logic or predetermined score balancing.

```text
player quality
+
formation geometry
+
tactical choices
+
live physical state
+
stochastic event outcomes
```

# 70. Final design rule

The central rule remains:

```text
ONE FOOTBALL CAUSE
        ↓
ONE DEFINED ENGINE PATH
```

Examples:

```text
position fit
→ usable player attributes

fatigue
→ readiness/action execution

formation
→ zone support and coverage

direction
→ route preference

pressing
→ opponent action pressure + fatigue + exposure

counter tactic
→ transition action preference

home advantage
→ calibrated creation / shot-quality shifts

luck
→ stochastic action and conversion draws
```

Do not re-add the same cause later as another generic signal.

The desired result is not merely a simulator that produces plausible aggregate statistics. It should generate individual matches whose possessions, territorial swings, tactical patterns, chances and commentary form a coherent football story, while the first-pass mathematics already gives team quality, tactics and luck approximately the intended relative influence.
