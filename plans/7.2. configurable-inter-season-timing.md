# Configurable Inter-Season Timing

This plan extends `plans/7. season-scheduler-overhaul.md` with a focused
change to the position of the inter-season workflow. It does not change the
league format, match schedule, or total season duration.

## 1. Goal

Split the existing seven-day gap between the final league match and the next
season into two configurable portions:

```text
interseasonAfterMatchDays = 2
interseasonBeforeNextSeasonDays = 5
```

With the current calendar this produces:

```text
Season Day 28  Final league match
Season Days 29-30  Post-match buffer
Season Days 31-35  Inter-season / next-season preparation
Next season      Starts after Season Day 35
```

The total season remains 35 days. The two values control the distribution of
the existing seven-day gap, not its length.

## 2. Calendar Rules

Retain `interseasonDays` as the canonical total gap and validate:

```text
interseasonAfterMatchDays + interseasonBeforeNextSeasonDays
    = interseasonDays

seasonDays
    = lastLeagueMatchDayIndex + 1 + interseasonDays
```

For the default calendar:

```text
lastLeagueMatchDayIndex = 27
interseasonDays = 7
seasonDays = 35
```

Derive the boundaries from the calendar rather than from literal day values:

```text
interseasonStartIndex
    = lastLeagueMatchDayIndex + 1 + interseasonAfterMatchDays

preparationStartIndex
    = seasonDays - interseasonBeforeNextSeasonDays
```

The two derived boundaries must be equal. With the defaults both equal index
30, which is human-readable Season Day 31.

The post-match buffer contains no league fixtures. The inter-season and
preparation window also contains no league fixtures. Transfers, auctions,
development, aging, payroll, loans, and other daily systems continue according
to their existing full-season cadence.

## 3. Configuration

Update:

- `backend/config/game.config.jsonc`
- `backend/src/config.ts`

Add the two settings with defaults `2` and `5`. Validate that they are valid
integer day counts and that their sum equals the canonical total gap. Keep the
derived `seasonDays` calculation unchanged apart from reading the total gap.

Legacy configuration normalization must remain safe. A legacy config that only
contains `seasonDays` or the old match-interval shape should preserve its old
timing, mapping the legacy gap to an immediate post-match transition unless
explicit new offsets are supplied.

Configuration changes must not silently leave already-materialized rollover
events at stale due dates. Either restrict changes to a new season/startup or
reconcile pending calendar-bound events during materialization while preserving
their idempotency keys.

## 4. Calendar Service

Update `backend/src/services/seasonCalendar.ts` to expose the new derived
values through `CalendarValues` and the `SeasonCalendarService` facade.

Use an explicit phase for the newly meaningful post-match buffer:

```text
ACTIVE       Competitive season and ordinary rest/preparation days
POST_MATCH   After the final match, before inter-season processing
INTERSEASON  Inter-season and next-season preparation window
```

Update `phaseForSeasonDayIndex`, `seasonSchedulePreview`, and schedule labels
to use the calculated boundaries. The preview must show post-match days and
inter-season days without hard-coded references to Days 29-35.

## 5. Scheduler and Rollover

Update `backend/src/services/scheduler.ts`:

- Keep `SEASON_RESULTS_FINALIZE` at the end of the final league match day.
- Schedule `INTERSEASON_START` and its dependent promotion, relegation,
  restructuring, waiting-pool, budget, contract, academy, and preparation
  events at `interseasonStartIndex`.
- Allow next-season fixture generation after preparation opens at that same
  calculated boundary.
- Keep final structure validation and rollover commit on the final day of the
  current season.
- Preserve event priorities, prerequisite checks, idempotency, retries, and
  downtime catch-up behavior.

The rollover coordinator must continue to execute unfinished steps in order if
the server is down or an administrator manually executes the final rollover
event. Moving the scheduled boundary must not bypass prerequisite enforcement.

## 6. Clock, World State, and Persistence

Update:

- `backend/src/services/gameClockService.ts`
- `backend/src/game/clock.ts`
- `backend/src/game/types.ts`
- `backend/src/game/world.ts`
- `backend/src/services/saveService.ts`

The game clock must:

- report `POST_MATCH` during the configured after-match buffer;
- report `INTERSEASON` from the calculated inter-season boundary;
- continue advancing through all `seasonDays`;
- perform the actual season rollover only after the final season day;
- reset the next season to Season Day 1 / index 0 with `ACTIVE` phase.

Existing saves containing only `ACTIVE` and `INTERSEASON` must migrate safely.
Fallback phase derivation must use the authoritative calendar service rather
than only comparing against `lastLeagueMatchDayIndex`.

The full `seasonDays` value remains authoritative for contract durations,
salary proration, loan periods, stadium timing, `DAYS_PER_YEAR`, and all other
season-length calculations. Neither new offset may replace it in financial or
duration formulas.

## 7. API and Frontend

Update the public/admin calendar surfaces:

- expose current season day, total season days, phase, and derived boundary
  information where needed by status and scheduler responses;
- update `frontend/src/api/client.ts` for the new phase and fields;
- update `frontend/src/screens/Admin.tsx` to display the new phase and use the
  server-provided season length for advance limits;
- update the admin season preview labels and boundary display;
- replace `frontend/src/screens/Dashboard.tsx`'s civil-month countdown with
  server-authoritative game-calendar information.

Audit civil-month-dependent helpers such as `nextPayrollTimestamp` and
`isSeasonOver`; competition timing must use the monotonic game calendar and
`seasonDays`, not the host calendar month.

## 8. Tests

### Configuration and calendar

Add or extend tests to verify:

- defaults are `2` after-match days and `5` before-next-season days;
- the values sum to the total seven-day gap;
- custom splits preserve the same `seasonDays`;
- invalid, negative, fractional, or mismatched values are rejected;
- legacy config input is normalized without changing its previous duration;
- phase and boundary indices are correct for multiple valid splits;
- the schedule preview contains no fixtures in either gap and uses derived
  labels.

### Scheduler and clock

Extend `backend/tests/scheduler.test.ts` and add focused season-calendar/clock
coverage for:

- results finalizing after the final match;
- transition events occurring at the configured boundary rather than always
  the day immediately after the final match;
- fixture generation and preparation timing;
- final validation and commit remaining on the last season day;
- post-match, inter-season, and rollover clock transitions;
- repeated materialization producing no duplicate events;
- retry, prerequisite, downtime catch-up, and coordinator idempotency behavior.

### Persistence and existing consumers

Add a save round-trip test covering phase migration and pending rollover state.
Update hard-coded calendar assumptions in existing tests, including:

- `backend/tests/worldgen.test.ts` config fixtures;
- `backend/tests/market.test.ts` post-season day references;
- any scheduler, worker, payroll, or economy fixtures that use literal season
  day values.

Retain and run the existing finance, economy, contract, loan, payroll,
development, and market tests to prove that full-season calculations still use
35 days and are unaffected by how the seven-day gap is split.

## 9. Documentation

Update the calendar, scheduler, preview, and acceptance sections of
`plans/7. season-scheduler-overhaul.md` to describe the two configurable
portions instead of assuming that inter-season processing starts immediately
after the final match.

Update references in
`plans/9. energy-injury-system-overhaul.md` so recovery continues across the
full seven no-match days while distinguishing the post-match buffer from the
inter-season/preparation window.

Remove hard-coded claims that inter-season always starts on Day 29 or that a
literal 35-day value is required where the runtime already has `seasonDays`.
